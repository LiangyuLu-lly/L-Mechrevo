## [Intel 大小核（P/E）分别倍频]（已暂缓 · 待真机条件）
- 结论（⭐ 只读调研所得，未在真机上执行过任何 MSR / 邮箱命令）：
  - ⛔ **现有通路做不到**：`source\PawnIO\IntelOcMailbox.cs` 只有 3 条邮箱命令（1=读能力 / 16=读值 / 17=写），domain 占 bits 40-47（编码 `(domain << 40) | (command << 32) | value`，见 `IntelOcMailbox.cs:23`、`:182`）；而 `ValidateDomain`（`IntelOcMailbox.cs:246-252`）**只允许 0/2、不可枚举**
  - `source\PawnIO\IntelOcDomain.cs:21-35` 里每个 domain 只有**一个 8 位标量倍频**（`Ratio` = Value 低 8 位、`MaximumRatio` = 能力位低 8 位），**没有 P/E/簇字段**
  - `source\MechrevoLite.Hardware\RuntimeCpuTuning.cs` 只探 `{0,2}`（`:381`），倍频仅在 `domain == 0 && !IsHybrid()` 时给出（`:391`）；`IsHybrid` = CPUID.07H:EDX bit15（`:1665-1672`）
  - 资源 `source\LMechrevo.IntelMSR.bin`（5,324 B，与 `_upstream\0.290.6\decomp\LMechrevo.IntelMSR.bin` **逐字节一致**）只导出通用 `ioctl_read_msr` / `ioctl_write_msr` / `cpuid` / `msr_read` / `msr_write` / `get_arch`，**无域表 / 无命令表**
- 协议层（⭐ 关键判断）：
  - 邮箱的 `domain` 是 **FIVR 电压平面选择器**（0=core / 2=cache），**不是核簇选择器** ⇒ 现有 ABI 里没有"P 核一套倍频、E 核另一套"的表达方式
  - 要分 P/E 只有两条路：
    - ① 固件在**另一个 domain** 再暴露一套 ratio（⚠️ **未验证**，且 `ValidateDomain` 现在不让枚举，连只读探测都发不出去）
    - ② 绕开邮箱走 MSR —— P 核 = `IA32_TURBO_RATIO_LIMIT 0x1AD` 的"按活跃核数 8 档表"；E 核需查 Intel SDM Vol.4「12/13 代 Performance Hybrid 附加 MSR」表，通常走 `IA32_HWP_REQUEST 0x774` 的 per-logical-processor max perf
- ⚠️ 上游作者 0.290.6 **也没给原因**：
  - 更新日志只说"Intel 电压偏移需能力检测和回读，非混合架构倍频受能力位限制"，**没有解释混合架构为什么整个不给倍频**
  - 反编译版（`_upstream\0.290.6\decomp`）**零注释**
  - ⭐ 我们代码里那句"混合架构上倍频语义不明确，故不给"（`RuntimeCpuTuning.cs:1662`）是**我们自己写的注解**，不是上游依据
  - ⇒ ⭐ 因此本条只能判为「**没实现 / 未验证**」，⛔ 不能判为「硬件不可能」，⛔ 也不能判为「实现了但不稳」
- ⚠️ 已排除的线索（XTU SDK 是死路）：
  - `IntelOverclockingSDK.dll` 版本 **6.4.1.24**（≈2019，早于 Alder Lake），254 个 knob 里只有"按活跃核数的倍频"与"逐核 RatioLimit"
  - `E-core` / `Efficient` / `Atom` / `Cluster` / `Hybrid` 在 6,265 条字符串里 **0 命中**
- 若要推进，需要（⭐ 清单）：
  - [ ] 一台**混合架构 Intel 真机**（如 Ultra 7 255HX / 275HX）上做一次**只读域探测**：仅为"读"放开 `ValidateDomain`，遍历 domain 0..7 各发 cmd1 / cmd16
  - [ ] 判据：若某域 `RatioSupported=1` 且其 Ratio 与 domain 0 **独立** ⇒ 才说明固件真的能分 P/E

- ⭐ 判据重定义（⛔ 不要再把「包里没有 log.txt」当正常现象）：
  - `日志\log.txt` **必须存在且有内容**（默认 all ⇒ 一定有；只有机主自己在 设置 → 日志级别 选过「关闭」、或用 LMECHREVO_LOG_LEVEL 覆盖才会没有）
  - `说明.txt` 开头应写「本次生效的日志级别 + 来源 + 打包时间」；`系统信息.txt` 的打包清单同样有这几行
  - `日志\内存日志缓冲.txt` 的容量现在是 4 MiB（声称 ~9 小时）；若里面仍只有几十 KB 且说明.txt 写着 64 KB ⇒ 装的是**旧包**
  - `日志\` 下的文件在打包时已按同一套规则打码（用户名/主机名/路径/序列号/MAC/GUID/长十六进制）——包内出现 `<用户名已打码>` 属预期

  - ① 段末「等机主重抓诊断包：看 GCU 版本 + `GPUDevice/Status parsed` 日志」—— 改前 log_level=off 时**这条根本看不到**（没有 log.txt），现在才真能看
  - ③「灯效复测（那位机主）：装新包 -> 不碰灯 -> 看键盘灯是否还活着」—— 同理：有了 log.txt 才有得看
- ⚠️ 仍待真机确认：机主包内 log.txt 的**实际覆盖时长**（取决于运行时长与日志速率；本机实测约 2 MB/h ⇒ 10 MiB 单代 ≈ 5 小时、4 代合计 ≈ 26 小时）

## [待办 · 40 系在 50 GCU 下的静音狂暴补丁]（新增，2026-10-22）
- 既有结论（2026-10-20，`docs/notes/GCU50-静音与性能档实现-20261020.md` 第 8/9 节）：
  - 40 系 + **40 GCU（1.0.2.70）** 没有 `SET_CPU_CORE_OFFSET_SILENT/EXTREME`，不能发静音狂暴子模式；
  - 静音狂暴能力位来自 **EC/WMI `WMIIsTurboSubModeSupport() == 0x55`**，换 GCU 版本不改变该返回值 ⇒ 当时结论是“不装 50 GCU 换静音狂暴”。
- 现状：LM 的“静音狂暴”按钮按注册表 `IsTurboSubModeSupport`（GCU 上报）放开；开发机 Gen40 + 50 GCU 实测该位 = false ⇒ 按钮隐藏。
- 本次要验证（只读优先）：
  1. 在 **40 系 + 50 GCU** 机器上直接读 WMI `WMIIsTurboSubModeSupport` 返回值（看是否 == 0x55=85）；
  2. 若为 85 ⇒ 做“补丁”：LM 不依赖注册表位，改为直接探测 EC/WMI 能力；能力成立时放开“静音狂暴”按钮，并走 50 GCU 的 `Fan/Control` 的 `SET_CPU_CORE_OFFSET_SILENT/EXTREME`；
  3. 确认 50 GCU 在 Gen40 上对这两个动作回 OK（可回滚、先只读/单机验证）；
  4. 若 WMI 返回不是 85 ⇒ 记录结论（硬件不支持），改为“自定义档模拟静音狂暴”（PL/温度墙/风扇保守化）。
- 待做：
  - [ ] 写只读 WMI 探测（`WMIIsTurboSubModeSupport`）并在开发机/目标机取值；
  - [ ] 核对 50 GCU `Fan/Control` 两个动作在 Gen40 的响应；
  - [ ] 能力成立时实现 capability override + UI 放开 + 日志（不成立则写结论）。

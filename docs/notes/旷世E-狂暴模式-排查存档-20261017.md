# 旷世E 不显示狂暴模式 —— 排查存档（2026-10-17）

> **用户结论**：「GCU 初始化仍然不支持 怀疑这个机器就是只有两个模式的 ⇒ 那就存档 不管先」
> ⇒ **本项结案，不改代码。** 本文只记录排查过程与结论，供以后同类问题参考。

---

## 一、现象

- 机型：**旷世E**（`Kuangshi E Series`）
- 板号：**`GS7AGHR`** · `family=ADL-DR4` · `sku=0001` · BIOS `N.1.00MRO02`
- CPU/GPU：**i7-12700H ＋ RTX 3070**
- 症状：**性能模式只显示两档（静音 / 平衡），不显示狂暴**
- 版本：`0.291.8.1`（**main 分支**，release line）
- 机主补充：**官方控制台会显示狂暴模式**

---

## 二、直接原因（已定死）

`TurboModeSupport` 这个**厂商能力位注册表值为 0**：

```
HKLM\SOFTWARE\OEM\GamingCenter2\ItemSupport
  TurboModeSupport (REG_DWORD) = 0        ← ⭐ 直接原因
  （同键下其它值）
  FanBoostBtnSupport = 1 · KeyboardSupport = 1 · NumPadSupport = 1
  OcSettingsSupport = 1 · ColorCalibrationSupport = 1 · DGpuDirectConnectionSupport = 1
  LightbarSupport = 0 · RGBLightbarSupport = 0 · TypeCSupport = 0 · LiquidCoolingSupport = 0
  IsAMDPlatform = 0 · IsNvGpu = 1 · IsHeroProject = 0 · IsProjectIdCommercial = 0
  ServiceReady = 1 · ServiceLoadingReady = 不存在 · PerformanceReady = 不存在
```

我们的代码（`main` 分支）：

```csharp
// FeatureMatrix.cs:28
new FeatureBitDefinition(FeatureBit.TurboMode, "TurboModeSupport", FeatureMissingPolicy.FailClosed)
// MechrevoDeviceCapabilities.cs:325
TurboMode = Flag(new string[1] { "TurboModeSupport" })
// SettingsForm.cs:7941
bool flag15 = Show(caps.TurboMode);
```

⇒ 读到 `0` ⇒ `Show(false)` ⇒ 按钮隐藏。**读法本身没有问题。**

日志印证：

```
[perf-row] 可见集=buttonSilent/buttonBalanced ... turbo=False silentTurbo=False custom=False turboVisible=False
```

## 三、排查过程与排除项

### ① GCU 变体 —— **不是问题，装的是对的**

按我们的判据（`installer-src\files\GCU\Select-GcuPayload.ps1` 的 `Resolve-GcuVariant`），
变体**按 GPU 代次**分：

```powershell
"GEN1020" { "1020" }   # 10/16/20 系
"GEN30"   { "30" }     # 30 系
"GEN40"   { "40" }     # 40 系
"GEN50"   { "50" }     # 50 系
default   { "50" }     # 未识别 ⇒ safety floor 用 50 系载荷
```

**RTX 3070 ⇒ `GEN30` ⇒ 30 系载荷。** 机主已自行确认"是 30 系"，与实际一致 ✅

各变体版本对照（本次实测导出，供以后快速认变体）：

| 变体 | GCUService | GCUBridge | 文件数 |
|---|---|---|---|
| **1020** | **1.0.2.47**（1,182,272 B） | **1.0.1.4**（58,000 B） | 175 |
| **30** | **1.0.2.70**（**1,769,216 B**） | **1.0.1.10**（**77,320 B**） | 173 |
| **40** | **1.0.2.70**（**14,447,864 B**） | **1.0.1.10**（**2,125,552 B**） | 71 |
| **50** | **1.2.0.0**（17,124,912 B） | 1.0.1.10（682,208 B） | 93 |
| **WJXY** | **1.0.2.70**（17,667,048 B） | 1.0.1.10（682,208 B） | 98 |

⚠️ **光看版本号区分不了 30/40/WJXY**（三者都是 `1.0.2.70` + `1.0.1.10`）⇒ **必须看文件大小**。

### ② 项目码不一致 —— **不是问题**

```
注册表 BIOS_PROJECT_ID          = IDR      ⇒ 枚举値 1
GCU 上报 Customize/Info ProjectID = 16      ⇒ 枚举値 ID1
EC 机型码原始字节                 = 16      ⇒ ID1
```

官方 `GCUService` 里的枚举：
```csharp
BIOS_PROJECT_ID { NA=0, IDR=1, IDX=2, IDV=3, IDO=4, IDP=5, IDS=6, IDY=7,
                  IDW=8, IDM=9, IDE=10, IDN=11, IDZ=12, IDXQ=13, IDQ=14, IDO3=15, ID1=16, ID2=17, ... }
```

⇒ **`IDR`(1) 与 `ID1`(16) 是两个不同的项目码，但来源不同**（BIOS DMI vs EC），
官方本来就分两条路存（`GetBiosProjctID()` 与 `m_ProjectID`）⇒ **不是"报错了一个"**。

### ③ 能力位不是按板号查表 —— 是 EC 报的

- 官方 `GCUService.exe` 里搜 `GS7AGHR` / `Kuangshi`：**Latin1 与 UTF-16 视图都零命中**
- `GetTurboModeSupport()` 与 `IsSupportLiquidCooling` / `IsSuportRamFan1p5` /
  `GetThermalProtectStatusFromEC` / `GetGPUCoreFreqFromEC` / `GetBiosProjctID` **是同一组方法**
  ⇒ 值来自 **EC**，不是从项目码表查的

### ④ 官方载荷里有 Turbo 档，但那只是出厂通用模板

`AiStoneService\MyControlCenter\UserPofiles\` 下 `Mode1~Mode4`：

| Mode | PL1 | PL2 | PL4 | GPU TGP | CoreOffset | 语义 |
|---|---|---|---|---|---|---|
| Mode1 | 80 | 80 | 215 | 150 | 0 | Gaming |
| Mode2 | 35 | 35 | 215 | 150 | 0 | Office（静音） |
| Mode3 | 95 | 95 | 215 | **175** | **+50** | ⭐ Turbo |
| Mode4 | 80 | 80 | 215 | 150 | 0 | Custom |

⚠️ 四个 `Activated` **全是 `false`** ⇒ 出厂通用模板，**不代表本机激活**。

### ⑤ 已排除：初始化未完成（这是本次的主要怀疑，但**被证伪**）

`ServiceLoadingReady` / `PerformanceReady` 两个"就绪键"**不存在**（只有 `ServiceReady=1`），
而我们的诊断器自己把这两个键缺失标成"重要线索" ⇒ 曾假设：
*"GCU 初始化没走完 ⇒ `TurboModeSupport` 停在默认 0"*。

**用户重启 GCU 后复测：仍然不支持** ⇒ ⭐ **该假设被证伪**，不是"读到未初始化值"。

### ⑥ ⚠️ 静态分析到此为止（天花板，务必记住）

`GCUService.exe` 反编译出 **4114 个桩方法**，全是 `throw new Exception("Runtime exception")`
⇒ **方法体被剥离**（`.NET Native` / 保护混淆），真实逻辑在 native 层
⇒ **"它具体怎么算出这个 0"无法静态确认**。

⇒ 凡是涉及 **GCU 内部算法/判定逻辑** 的问题（"某个能力位怎么算出来的"），
**静态分析基本走不通**，只能靠**真机行为对照**。

## 四、结论

**这台机器（旷世E `GS7AGHR` · i7-12700H ＋ RTX 3070）很可能就是只有两档（静音 / 平衡）。**

依据：
1. `TurboModeSupport = 0` 由 GCU 写入，而该值来自 **EC**
2. GCU 变体**正确**（30 系，与 RTX 3070 相符）⇒ 不是装错载荷
3. 项目码不一致**有合理解释**（来源不同）⇒ 不是错配
4. 能力位**不按板号查表** ⇒ 不是机型识别错误
5. GCU 重启初始化后**仍然不支持** ⇒ 不是"读到未初始化值"

⇒ **我们隐藏狂暴模式的行为是正确的**（遵循厂商能力位），**不是 bug，不需要改**。

### 关于"官方控制台会显示狂暴模式"

⚠️ 这条与 `TurboModeSupport=0` **不一致**，但：
- 可能机主看到的是**官方 UI 固定渲染四档、该档灰掉/不可用**（官方 UI 是通用模板驱动，见上表 `Activated` 全 false）
- 也可能官方不读这个注册表键、直接问 EC
- **已超出静态分析能验证的范围**（GCUService 方法体剥离）

**决定：不再追。** 若以后要追，唯一可行路径是**真机抓官方控制台对 EC 的读写**，
而不是继续静态分析。

## 五、遗留问题（与本项无关，但本次排查发现）

### ⚠️ 诊断器的「底座目录」判错 —— 导致 `[GCU 关键文件]` 全节误报"缺失"

诊断包实际输出：

```
[GCU 关键文件]
  底座目录: D:\L-Mechrevo        ← ⛔ 错，实际是 D:\L-Mechrevo\GCU
  布局判定: A（<root>\AiStoneService\…）
  AiStoneService\GCUBridge.exe                    → 缺失   ← ⛔ 误报
  AiStoneService\MyControlCenter\GCUService.exe   → 缺失   ← ⛔ 误报
  ...（5 个关键文件全报缺失，大小/版本/SHA256 一个都没采到）
```

**实际情况**（同一份诊断包的另一节已经证明了）：

```
GCUBridge 进程 PID=4240 路径=D:\L-Mechrevo\GCU\AiStoneService\GCUBridge.exe 文件版本=1.0.1.10
GCUService 进程 PID=12992 路径=D:\L-Mechrevo\GCU\AiStoneService\MyControlCenter\GCUService.exe 文件版本=1.0.2.70
```

**根因**：`HKLM\SOFTWARE\L-Mechrevo` 这个键**不存在**（GCU 是手动/绿色安装，没走我们的安装器、
没写 `GcuServiceDir`/`GcuServiceExe`/`GcuVariant`）⇒ 诊断器退回默认候选 `D:\L-Mechrevo\`，
而漏了 `\GCU` 这一层。

**建议修法**：**从运行中进程的 `ImagePath` 反推目录**，比靠注册表/默认候选可靠得多。
（本次未改，留待单独处理。）

### 备注：本次无法从诊断包直接读 GCU 变体

因为上面那个 bug，`GCUService.exe` 的**大小**没采到 ⇒ 而 30/40/WJXY 版本号完全相同
⇒ **只能靠文件大小区分**。修好底座目录后这一项就能自动判定。

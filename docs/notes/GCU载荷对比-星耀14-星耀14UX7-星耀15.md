1. ⭐⭐ **A 与 C 完全可互换**：两者共有 15 个同名文件，**SHA256 逐字节全同（15/15 SAME）**，

## 四、机型相关键 + 它们【确切写在哪个文件】（⭐ 最有价值的部分）

### 4.1 ⭐⭐ 机型串的真身 = `UserFanTables\` 的**目录名**（唯一权威机型表）

- ⭐ 位置：`B ...\UserFanTables\<MODEL_ID>\M{1,2}T{1,2,3}.json`（仅 B 有，144 文件）
- ⭐ **24 个 MODEL_ID**（逐字）：
  `PH4AQE3` `PH4AQxx` `PH4ARxx` `PH4AUxf` `PH4AUxx` `PH4AXxx` `PH4PGx1` `PH4PGx2` `PH4PRxx` `PH4PUxx`
  `PH4TQx1` `PH4TRX1` `PH4TUX1` `PH6AQxx` `PH6ARxx` `PH6PG0x` `PH6PG0x150W` `PH6PG3x` `PH6PG3x150W`
  `PH6PG7x` `PH6PG7x150W` `PH6PGEx` `PH6PRxx` `PH6TRX1`
- ⭐ 命名规律（⭐ LM 可据此解析）：`PH4*` = 上一代平台（含 AMD `AU`/`AX` 段），`PH6*` = 新一代平台；
  `PG` = 带独显机型，`PG` 后缀 `150W` = 高功耗档；`AQ/AR/PR/PU/TR/TU` = 不同模具/散热区分。
- ⚠️ **`XY14` / `XY15` / `星耀` / `无界` 这些营销名在包内【一次都没出现】**（对 5.56 与 5.57 两个安装器都做了 ASCII 串搜索，命中数均为 0）。
  ⇒ ⭐ 机型判据只能用 **`PH4*`/`PH6*` 平台码**，不能用「星耀14/星耀15」字样。

### 4.2 ⭐ 键名与语义（`M{1,2}T{1,2,3}.json`）

文件名两位 = **两维矩阵**（由数据实测归纳）：
- `M1` = **AC（接电源）**，`M2` = **DC（电池）** —— 依据：M1 组 PL1 恒高于 M2 组，且 `PL1_dc/PL2_dc` 另以 `0`/`NA` 单独存在；
- `T1/T2/T3` = **性能档位**（节能/平衡/性能）—— 依据：同模型内 T1 < T2 < T3 的 PL1 单调递增（如 `PH4AUxx`：30/32/38、`PH4TRX1`：35/50/60）。

每个 JSON 的**结构键**（以 `PH4AUxf\M1T1.json` 与 `PH6PG0x\M1T1.json` 实测）：

| 键 | 含义 | ⚠️ 机型差异证据 |
|---|---|---|
| `Activated` / `Name` | 启用位 / 表名（`M1T1`） | 全表一致 |
| `PL1` / `PL2` | 长时/短时功耗墙 | ⭐ **逐机型不同**（见 4.3） |
| `PL1_dc` / `PL2_dc` | 电池态覆盖值 | 多为 `0` |
| `TCC` | 温度墙偏移 | `-5`，AMD 老平台 `PH4TQx1/PH4TRX1/PH4TUX1/PH6TRX1` 为 **`NA`** |
| `CTGP` / `CTGP2` | Configurable TGP（显卡动态功耗） | ⭐ **仅独显机型有**（`PH4AQE3`/`PH4PGx*`/`PH6PG*`/`PH6PGEx`） |
| `DB` / `DB2` | Dynamic Boost | ⭐ **仅部分机型有**，`PH6PG0x` 一代才有 `DB2` |
| `WM` | 风扇/水冷策略位 | 多为 `NA` |
| `CpuTemp_DefaultMaxLevel` / `GpuTemp_DefaultMaxLevel` | ⭐ **风扇曲线档位上限**（8 / 11 两族） | ⭐ **PH4 多为 8，PH6 多为 11** |
| `CPU[16]` / `GPU[16]` | 16 段风扇曲线，每段 `{ID, UpT, DownT, Duty}` | ⭐ **逐机型逐档不同** |

## 五、通用性结论（⭐ 明确写）

| 组合 | 能否互换 | 依据 |
|---|---|---|
| **A ⇄ C**（星耀14 AMD 无界14 ⇄ 星耀15） | ⭐⭐ **可以，完全等价** | 15/15 共有文件 SHA256 全同；安装器与 84 MB msix 同一哈希 |
| **B ⇄ A/C** | ⛔ **不可以** | UI 世代换代（CCU.WinUI→ControlCenter3）、包格式换代、5.56 vs 5.57、且 B 独占 144 机型表 |
| **A/C 单独装机** | ⚠️ **缺 24 机型风扇表** | 两份都**没有** `UserFanTables\` ⇒ 换用 A/C 会**丢失逐机型风扇曲线** |
| **B 单独装机** | ⚠️ 覆盖机型最广（24 个 PH4/PH6） | 但它是**较新 UI 世代**，与 LM 现有 5.56 世代载荷不同源 |

⭐ (c) **卡住的差异（必须与机器匹配的）**，按重要性排序：
1. ⭐⭐ **`UserFanTables\<PH4*/PH6*>\M{1,2}T{1,2,3}.json` 的目录名 = 机型码** —— 用错机型 ⇒ **功耗墙与风扇曲线全错**（可能过热或性能受限）；
2. ⭐ **`RGBKeyboard.reg` 的 23 个子键**（`MEZone_*_97..104`、`2nd/2p1nd/3nd/3p1nd`）—— 用错 ⇒ 键盘灯分区错位；
3. ⭐ **UI 包世代**（`CCU.WinUI 5.56.1.18` vs `ControlCenter3 5.57.1.2`）—— 与 `setup.ini` 的 `CustomizeTarget 56/57` 绑定；
4. ⚠️ `CTGP/CTGP2/DB/DB2` 的有无 —— 独显机型才该有，错配会写不存在的控制项。

⭐ **LM 需要检测/切换的信号**（⭐ 以数据为准的排序）：
- ⭐ **`PH4*/PH6*` 平台码** —— 唯一被载荷本身使用的机型键（目录名）；
  最可能的读取来源：**SMBIOS / `Win32_BaseBoard.Product`** 或 **BIOS 项目码**（⚠️ 静态未证实，见 ⑥）；
- ⚠️ **不能**靠「星耀14/星耀15/无界14」等营销名（⭐ 包内 0 命中）；
- ⚠️ **不能**只靠现有 `Select-GcuPayload.ps1` 的 **dGPU 世代（RTX 30/40/50）** —— 与机型码**不是同一维度**；
- ⚠️ 现有脚本第 68-69 行明确写：**`-BiosProjectId` 被接收但刻意不作为检测输入**（"the platform code must not decide the dGPU generation"）。
  ⇒ ⭐ 若将来要用平台码选**机型载荷**，这是**新增的第二条判据**，⛔ 不应改写原有 dGPU 世代判据。

## 六、LM 要支持这些机型需要做什么（⭐ 建议，⛔ 待用户点头）

⭐ **能白送的（共享核心，无需机型判断）**：
- ⭐ `logo\` 全部（图标、协议 HTML/RTF、`Language\*.json`）、`PreinstallKit\Add-AppDevPackage*` 全家、
  `Dependencies\x64\Microsoft.WindowsAppRuntime.1.7.msix`（A/C 侧）—— 这些**与机型无关**；
- ⭐ 结论：**约 15 个「共享核心」文件 + 语言/许可/依赖**可直接复用，占 A/C 体积的绝大部分（≈135 MB / 141 MB）。

⭐⭐ **必须按机型切的三样**：
1. **风扇曲线/功耗墙**：`UserFanTables\<机型码>\*.json`（144 个文件，6 档 × 24 机型）；
2. **键盘灯映射**：`RGBKeyboard.reg` 的 `MEZone_*` 子键族；
3. **UI 世代 + `CustomizeTarget`**：56（CCU.WinUI）vs 57（ControlCenter3）。

⭐ **一条具体的下一步建议**：
⛔ **先不要换 LM 现在随包发的 GCU 载荷或选择器**（用户只授权「结果可以放进去」）。
建议按顺序做：
1. ⭐ **先做只读探测**：在真实星耀14 UX7 / 星耀15 机器上，**只读**采集能反映 `PH4*/PH6*` 的信号
   （`Win32_BaseBoard.Product`、`Win32_ComputerSystem.Model`、BIOS 项目码），**先确认哪个字段真能对上 24 个机型码**；
   ⚠️ 在未确认之前，任何「按机型选载荷」的代码都**不该写**；
2. ⭐ 若确认了信号源，**新增**一个「机型维度」到载荷数据（`gcu-variants.json`）与选择器，
   ⛔ **不动**现有 dGPU 世代分流逻辑（两条判据正交，可并存）；
3. ⭐ 选择依据 = 「**dGPU 世代**选服务三件套」+「**平台码 `PH4*/PH6*`** 选 `UserFanTables` 与键盘灯表」；
4. ⚠️ A 与 C 既然完全等价，⭐ **只需保留一份**（可省 ≈141 MB 或一份 84 MB msix 的重复）。

| `OSDTpDectect/Control`（UTF-16LE） | ✅ ×1 | ✅ ×1 | ✅ ×2 | ✅ ×1 | ✅ ×1 | ✅ ×2 |
| `OSDTpDectect/Language`（UTF-16LE） | ✅ ×1 | ✅ ×1 | ✅ ×2 | ✅ ×1 | ✅ ×1 | ✅ ×2 |
| `OSDTpDectect/Close`（UTF-16LE） | ⛔ ×0 | ⛔ ×0 | ✅ ×2 | ⛔ ×0 | ⛔ ×0 | ⛔ ×0 |
| 常量名 `OSDTpDectect_Control`（ASCII） | ✅ ×1 | ✅ ×1 | ✅ ×1 | ✅ ×1 | ✅ ×1 | ✅ ×1 |
| 常量名 `OSDTpDectect_Language`（ASCII） | ✅ ×1 | ✅ ×1 | ✅ ×1 | ✅ ×1 | ✅ ×1 | ✅ ×1 |

⛔ **没有任何一格是"无"** ⇒ ⭐ 原结论"两代正好互换、A 的检测器里根本没有 `Control`（反之亦然）"**⛔ 错**。
⭐ **唯一真实差异**：`OSDTpDectect/Close` —— ⭐ **A 有、B 无**（⭐ 这才是两代之间唯一的真区别）。

##### (b) ⭐⭐ 原结论错在哪：**奇偶对齐假象**

`GCUService.exe` / `DefaultTool.exe` 里这两个主题名**不是 .NET 用户字符串**（⛔ 不在 `#US` 堆），
而是 ⭐ `MyControlCenter.Topic` 类的 **`const string` 字段默认值**（⭐ 存在 `#Blob` 堆，UTF-16LE）：

```
MyControlCenter.Topic::OSDTpDectect_Language   // blob 0x6074, 长 0x2A = 42 字节
MyControlCenter.Topic::OSDTpDectect_Control    // blob 0x609F, 长 0x28 = 40 字节
```

⇒ ⭐ `Language` 在前、`Control` 在后，**两个字符串起始偏移只差 43 字节（奇数）**。
⇒ ⚠️ 用"按 2 字节步长扫 UTF-16LE"的朴素抽取器，**同一时刻只能看到其中一个**，
   看到哪个取决于它从哪个偏移起步 ⇒ ⭐ A 抽到 `Control`、B 抽到 `Language`。
⛔ **这不是文件内容的差异，是抽取器的假象。**

⭐⭐ **反证（决定性）**：该区段 **A 与 B 逐字节相同** ——
`A GCUService[0xA205D9..]` ≡ `B GCUService[0x935450..]`（125 字节全等）；
`A DefaultTool[0x113C7D..]` ≡ `B DefaultTool[0x1139D6..]`（全等）。
⛔ 若真"对调"，这两段字节不可能相同。

##### (c) ⭐⭐ 每个出现点是【发布】还是【订阅】

| 文件 | 判定 | IL 级依据 |
|---|---|---|
| `GCUService.exe` / `DefaultTool.exe`（A、B 同） | ⚠️ **只有主题名常量，⛔ 分不出调用点** | ⛔ 这两个主题名**在 IL 里没有任何 `ldstr`**（⭐ 全量 6858 / 6840 个方法逐个反汇编确认 = 0 处）；⭐ 常量只在 `MyControlCenter.Topic` 里定义，⛔ **其使用点所在的 `MqttClientCtrl` 全部方法体被厂商抹成桩**（`ldstr "Runtime exception"; newobj Exception; throw`，⭐ A 5434 处 / B 5426 处）。⇒ ⭐ **如实说：分不出发布还是订阅** |
| `OSDTpDetect.exe`（A、B 同） | ⭐⭐ **订阅**（确证） | ⭐ `MQTTDatsService::InitlizeTopics` 把 `OSDTpDectect/Language`、`/Control`（A 另有 `/Close`）逐个 `Add` 进 `TopicList`；⭐ `ClientConnection` 里 `newobj MqttClient(localhost, 13688)` → `Connect` → ⭐ **`Subscribe(keys, values)`**（⭐ 把 `TopicList` 全部订阅） |

⚠️ **间接证据（GCU 侧）**：⭐ `MyControlCenter.Topic` 里这些常量**只有主题名、没有 payload**
⇒ ⭐ 更像"订阅过滤表 / 主题白名单"，⚠️ 但 ⛔ **静态无法证实**。

##### (d) ⭐⭐ 两个主题的语义：**各自独立的单向通知，⛔ 不是一问一答**

⭐ `OSDTpDetect.App::<MQTTDatsService_DataChange>::MoveNext`（A/B 同构）逐个 `op_Equality` 比较后**各走各的分支**：

```
ldstr "OSDTpDectect/Control"  -> 分支①        (A 另有) ldstr "OSDTpDectect/Close" -> 分支③
ldstr "OSDTpDectect/Language" -> 分支②
```

⇒ ⭐ **一个主题一个独立处理分支** ⇒ ⭐ 是**并列的下行通知**，⛔ 不是"请求 / 响应"。
⭐ 这正好解释了原表的"矛盾"：⛔ 原表把**两个并列通知**误当成**一问一答**，才推出"原配不通、交叉反而通"的怪结果。

⚠️ **补充**：⭐ **检测器自己也会发布** —— `App::SendTopicToServer` → `MQTTDatsService::PublishTopic`
→ `MqttClient::Publish`，⭐ 发的是 **`Setting/Control`**（`TOUCHPAD_LED_ON` / `_OFF`）与 **`Languages/Control`**（`GET`），
⛔ 不是 `OSDTpDectect/*`。

##### (e) ⭐⭐ 更正后的结论：**可以混装**

- ⭐ `GCUService.exe` / `DefaultTool.exe` **从不与 `OSDTpDetect.exe` 通过 MQTT 对话**（见 (c)）；
- ⭐ 检测器连的是 **`localhost:13688`**、clientId `MyTPDetector` ⇒ ⭐ 连的是 **`GCUBridge.exe` 起的本机 broker**；
- ⭐ A 与 B 的检测器**订阅的都是 `Language` + `Control` 的全集**（⭐ 常量名在两代**完全同名**，`Topic::OSDTpDectect_*` 都在）；
- ⇒ ⭐⭐ **`GCUService.exe`(A/B) × `OSDTpDetect.exe`(A/B) 四种交叉组合，都不会因主题名而"静默失效"**。

⚠️ **唯一真实的混装风险**：⭐ **A 的服务若发 `OSDTpDectect/Close`，而配 B 的检测器**（B 不订阅 `Close`）
⇒ ⭐ **"关闭 OSD"这一条动作会静默失效**（⭐ B 只处理 `Control` / `Language`）。
⛔ 反向（B 服务 + A 检测器）**无此风险**（⭐ A 订阅的是超集）。

⇒ ⭐⭐ **原"必须同侧"结论【降级】为"建议同侧"，⛔ 不是硬约束**：
`GCUService.exe` + `GCUBridge.exe` + `GCUUtil.exe` + `OSDTpDetect.exe` ⭐ **建议整组取用**（省心、少一类变量），
但 ⛔ **不是"不能混"**；⭐ 若要混装，⭐ **只需保证 `OSDTpDetect.exe` 取 A 那份**
（⭐ 超集：多支持 `Close`，且 FileVersion `2.0.0.1` vs B `0.0.0.0`）。

#### 10.3.2 ⭐⭐ `acpi\INOU0000` 是【通用平台 ID】——两份 INF 逐字节写着同一个硬件 ID

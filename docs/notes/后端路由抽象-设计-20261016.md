|---|---|---|

| 机制 | 位置 | 作用 |
|---|---|---|
| `Capabilities` 能力位 | `BaolongdaBackend.BuildCapabilities()` 是**宝龙达的唯一来源**；消费点只在 `MechrevoHw.ApplyBaolongdaBackendAsync` | 「能不能做这件事」的既有表达 |

## 4. 设计

### 4.1 后端路由枚举（预留 `AcpiEc`）
```csharp
internal enum BackendRoute
{
    None = 0,
    Gcu,
    LegacyMifs,
    Baolongda,
    AcpiEc,      // 预留：即使尚未实现
}
```

### 4.2 功能项枚举
```csharp
internal enum BackendFeature
{
    PerfModeSwitch, CustomProfileApply, PowerLimit, ChargeLimit,
    KeyboardLighting, LogoLight, Lightbar,
    GpuModeSwitch, FanRpmRead, FanCurveRead, FanCurveWrite,
    FnLock, Touchpad, OsdToggle, Temperature, RefreshRate,
    // …按需增加
}
```

### 4.3 三态（本设计的核心）
```csharp
internal enum FeatureSupport
{
    Supported,                 // 当前后端已接好下发路径，可现在就走
    NotSupportedByThisBackend, // 当前后端做不到 —— 但别的后端可能能做
    Unknown,                   // 尚无法判定（例如还没探测完）
}
```

> **本会话反复踩的坑正是把中者当成了「永远不行」** ——
> 例如「以 GCU 未连接为由阻断」，把一个 `NotSupportedByThisBackend`
> 误当成终局结论，于是整体失败。

### 4.3.1 语义（必须严格）

- `Supported` ⇒ **当前后端接好了这条下发路径**，调用方**可以**按该后端的路径执行。
- `NotSupportedByThisBackend` ⇒ 调用方**不得**假装成功；要么走自己的原路，
  要么**如实告知用户「本机不支持」**。
- `Unknown` ⇒ 探测尚未完成，**不代表不支持**；调用方应保守行事（例如等一轮再问）。

> ⚠️ **它不是「硬件一定支持」的证明，也不是 `IsGcuConnected` 的替代品** ——
> 它回答的是「**谁的路径**」，**不是「通不通」**。
>
> ⚠️ 铁律不变：**能力位 = 已接好下发路径，不等于硬件支持**。
> 因此 `Query()` 的每一项都要与实际下发路径**同时**落地，否则又是一次「点了没反应」。

### 4.4 查询入口
```csharp
// MechrevoHw
internal BackendRoute ActiveRoute { get; }           // 当前生效后端
internal FeatureSupport Query(BackendFeature f);     // 三态查询
internal bool TryRoute(BackendFeature f, out BackendRoute route);  // 便捷版
```

### 4.5 实现骨架（纯查表、无副作用）
```csharp
internal FeatureSupport Query(BackendFeature f)
{
    if (IsGcuConnected)      return GcuSupports(f);
    if (UsesBaolongda)       return BaolongdaSupports(f);
    if (UsesLegacyMifs)      return LegacyMifsSupports(f);
    return FeatureSupport.Unknown;   // 后端尚未就绪，不代表"不支持"
}
```

`BaolongdaSupports(f)` **必须复用** `BuildCapabilities()` 的产出，
**不允许**出现第二份互相打架的后端事实。

## 5. 与既有机制的关系（谁是唯一事实来源）

| 机制 | 角色 | 消费者 |
|---|---|---|
| `BuildCapabilities()` | **后端的唯一事实来源** | `Query()` 内部读它 |
| `Query(f)` / `FeatureSupport` | 「这个动作该走谁」 | **执行层**（服务/表单的动作入口） |
| `Capabilities` 能力位 | 「界面该显示/启用哪些控件」 | **UI 层** |
| `RuntimeModelSupport` | 「这台机型整体受不受支持」 | UI 层（整块降级） |
| `IsBaolongdaModelWhitelisted` | 板号判据 | `BaolongdaBackend` |

**分层原则**：
- **事实** 只有一份（`BuildCapabilities`）。
- **路由**（本设计）是事实的一个**视图**，供执行层用。
- **UI 可见性** 继续用能力位，**不因本设计而改变**。

## 7. 附带发现：`FirmwareSlot` 模型本身是错的

参考实现（`_refs/JiaolongControl`，MIT，只取协议事实）：
- `JiaoLongConfig.cs`：`CpuFanCurve` / `GpuFanCurve` 是 `List<FanPoint>`，**存在应用自己的配置里**；
- `AutoFanControl.cs:212`：读配置点 → **轮询温度 → 写风扇转速**；
- ⇒ 真实生态里**没有「固件槽」概念**。

推论：
- 把自定义档映射成 `PerfModeRoute.FirmwareSlot` 是**模型错误**；
- 它同时卡住了 `BaolongdaFanCurveStore.cs:15`；
- **修正方向**：「档位」与「风扇曲线」**解耦** —— 档位是后端的模式切换，
  风扇曲线是**软件引擎 + 周期写转速**（功能号 20/21）。

这与路由层**正交**，应作为独立任务排期。

|---|---|---|---|
| 1 | 新增 `AcpiEcBackend.cs`（探测 + 读写） | 新文件 | 大（但**一次性**） |
| 2 | `AcpiEcSupports(f)` 查表分支 | `MechrevoHw.cs` | ~20 行 |

| 4 | `BackendRoute.AcpiEc` 已有（本设计预留） | — | 0 |

**合计：3 处编辑、约 25 行 + 1 个新文件。**

> **对比不做的情形**：需要重扫全部 `IsGcuConnected` 调用点（~48 处），
> 逐个判断是否误判，并修改其中 8 处 A 类 —— 且**每加一条后端就要重来一次**。

**这就是核心验收标准**：新增后端时，**调用方零改动**。

### 8.1 验收标准（整体）

1. 调用方**不再**直接问 `IsGcuConnected` 来决定**非 GCU 专属**的操作。
2. 新增一个后端时，**修改点只有**：后端实现 + `XxxSupports` 查表 + 探测顺序。
3. 任何「不支持」的情形，**用户能看到准确文案**，而不是「点了没反应」或错误的失败原因。
4. 非目标机型**逐位不变**（用 `git diff` 的「纯增 / 局部改」规模自证）。
5. 能力位与实际下发路径**同时**落地 —— 不允许出现「能点但没接好」。

### 8.2 `AcpiEc` 的目标机型与优先级（**用户已决策**，2026-10-16）

用户原话：

> 「D的话同方看有没有GCU 有GCU先GCU，其他的本来就是不是GCU路子的」

拆开：

| 机型 | 判据 | 走哪条 |
|---|---|---|
| **同方，有 GCU** | `IsGcuServiceInstalled` 为真 | **GCU 优先** |
| **同方，无 GCU** | 上面的判据为假，且不是宝龙达 | **ACPI/EC** ← ⭐ `AcpiEc` 的**首要目标** |
| 宝龙达模具 | 板号 `MRID6-*` | WMI `MICommonInterface`（已有后端，与 `AcpiEc` 并列、互不取代） |
| 老同方（无 GCU、无宝龙达） | 落到老接口 | `LegacyMifs` |

**关键结论：`AcpiEc` 的首要目标机型 ＝ 同方【无 GCU】的机型。**
不是「所有非 GCU 机型」（宝龙达已有自己的后端），也不是「宝龙达的替代」。

因为 ACPI/EC 与 GCU 服务的是**同一批功能**（性能档 / 自定义档 / 功耗墙 / 风扇 / 显卡模式 / 灯光 …），
所以 **`BackendFeature` 不需要增减项** —— 加后端时只是补一份 `AcpiEcSupports(f)` 登记。

#### 与既有探测顺序的核对（**一致** ✅）

`MechrevoBackendOrder.Candidates`（`source/MechrevoLite.Hardware/MechrevoBackend.cs:73`）实测顺序：

| # | 候选 | 条件 |
|---|---|---|
| 1 | `Gcu` | 仅当 `IsGcuServiceInstalled` ⇒ **这就是「有 GCU 先 GCU」** |
| 2 | `Baolongda` | `BaolongdaBackend.TryCreate()`（含真读功能号 22 的活体判据） |
| 3 | `LegacyMifs` | `LegacyMifsWmi.TryCreate()` |
| 4 | `Gcu` | 无条件哨兵（兜底，表现为「GCU 未连接」而不是「选错后端」） |

⇒ **用户的原则在代码里已经成立** ✅ —— 同方机型装了 GCU 就优先 GCU；没装才往非 GCU 的后端落。

#### `AcpiEc` 的插入位置建议

**插在第 3 与第 4 之间**（即 `LegacyMifs` 之后、无条件 GCU 哨兵之前）：

- ⛔ 不能在第 1 位之前 —— 有 GCU 的机器必须先走 GCU（用户明确要求，且 `MechrevoBackend.cs:82` 的注释也这么写）。
- ⚠️ 不能在第 4 位之后 —— 第 4 位是**无条件非 null 哨兵**，放它后面就**永远轮不到**。
- 放在 `LegacyMifs` 之后是因为老接口是**既有可用**的后端，保持向后兼容优先。

⚠️ 本节的顺序核对**只做只读确认，未改任何代码**。

## 9. 风险与分步

### 风险
| 风险 | 缓解 |
|---|---|
| 路由层与能力位出现第二份事实 | `BaolongdaSupports` **强制**读 `BuildCapabilities` |
| 误伤 B 类 40 处 | 本设计**不要求**改它们；迁移清单只含 A 类 |

| 引入新抽象反而增加理解成本 | 骨架仅 1 枚举 + 1 查询 + 3 查表，**无依赖注入、无接口** |

### 分步
0. **第 0 步（已完成，作为前提）**：宝龙达接入框架、能力位单一来源、意图方法模板；
   灯光 / 显卡模式 / 三档高亮 / 删 EC 开关 / 空档＋文案 / 键盘灯颜色亮度 / 诊断可见性 /
   固件预检误拒 / OSD 本地化 / 自定义档诚实性 —— 共 10 条已落地。
1. **第 1 步（零硬件风险）**：落 `BackendRoute` / `BackendFeature` / `FeatureSupport`
   + `Query()` 骨架，**只搬既有事实，不新增能力**；同时修 ⑤⑥ 文案。
2. **第 2 步**：迁 ③④⑦，每处**先接真实路径再换判据**（否则如 ④ 的「拆闸无用」）。
3. **第 3 步（独立排期）**：§7 的风扇曲线软件引擎。
4. **未来**：接 `AcpiEc`，按 §8 验证「3 处编辑」。

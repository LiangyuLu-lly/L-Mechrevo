## 一、⭐ 模具归属（最容易搞错、代价最大的一条）

**同一个形式的功能，两家模具的实现完全不同，不能互相参考。**

| 维度 | 同方模具 | 宝龙达模具 |
|---|---|---|
| 代表机型 | 翼龙15Pro（本机开发机）、`GM5HG0A` | 蛟龙系列 `MRID6`（机主机）、`R9 7945HX`/`8745H` |
| 官方控制台 | `ControlCenter_5.17.51.34` / `5.56.60.34_GX`（`GamingCenter2`/`GamingCenter3` 代） | **`JiaoLong7.3`**（主程序集 `第三方蛟龙游戏控制中心.dll`） |
| WMI 后端 | `AcpiTest_MULong`（免驱）；主用 `\\.\ACPIDriver` | `MICommonInterface`（`ACPI\PNP0C14\MIFS_0`） |
| EC 通道 | `\\.\ACPIDriver`＋H2RAM 窗口 `0x700–0x7FF`（`UWACPIDriver.sys`，WHQL 签名） | 该设备**打不开**（`Win32 error 2`）⇒ 须走端口 I/O（`0x62`/`0x66`）或官方那套 `0x2E`/`0x2F` |
| 充电/功耗寄存器 | H2RAM `0x07xx`（`0x07B9`/`0x07D0`/`0x7C3`/`0x0742`/`0x087F`/`0x0770`）—— 上游 `Leo-stro/mechrevo-charge-limit` | **XRAM `0x81xx`/`0x84xx`**（`0x8150` mailbox、`0x8153`/`0x8154` 阈值、`0x83C0` 模式、`0x847C` SOC、`0x8410-0x8413` 版本） |
| 物理内存窗口 | — | `OperationRegion (ECF2, SystemMemory, 0xFE800400, 0xFF)`（DSDT 声明，**长仅 0xFF**） |
| 校色 | 官方有（`GamingCenter2` 的注册表键 `...\DisplayFeatures\ColorCalibration`） | **官方没有**（`JiaoLong7.3` 反编译零命中）⇒ 只能用 Windows 标准 API |

### ⚠️ 已经因此踩过的两次坑
1. **限充**：我们拿同方那套 H2RAM `0x07xx` 去蛟龙上找充电寄存器，读回 `0xFF` 就判"固件不支持限充"
   —— **错在去错了窗口**。真正管用的是宝龙达的 XRAM `0x81xx`（`JiaoLong16Pro-Battery-threshold`，`MRID6`/`BM5235`）。
   连当时代码注释都怀疑过"`0xFF` 更像未映射填充值"，可惜结论还是判了不支持。
2. **校色**：曾认为"同方那两个 `ControlCenter` 包里可能藏着校色的厂商实现"——
   **作废**，那是同方模具的，对宝龙达没有参考价值。（用户明确指正）

⇒ **规矩：拿到任何材料，先标模具归属；跨模具的结论一律不成立。**

### 关键协议事实（只取事实）
```
端口 0x66 = 状态/命令   端口 0x62 = 数据
读：向 0x66 发 0x92 → 经 0x62 依次传「地址高字节、地址低字节」→ 从 0x62 读数据
写：向 0x66 发 0x93 → 经 0x62 传「地址高字节、地址低字节、数据」

XRAM 地址表：
  0x8150 Mailbox 主命令（写 0x10 触发）     0x83C0 模式
  0x8151 子命令/参数                         0x8370 状态
  0x8152 结果（0x55 成功 / 0xAA 未知子命令）  0x847C SOC
  0x8153 原生阈值上限                        0x8410~0x8413 EC 版本
  0x8154 原生阈值下限                        0x8460 标志位
子命令：0x0D 启用原生阈值 / 0x0E 停充 / 0x0F 恢复
模式值：0x00 正常 / 0x02 停充 / 0x48 原生阈值模式
```
- **地址表三重独立确认**：① EC 固件里 `MOV DPTR,#addr` 硬编码（`0x8153` 被引用 42 次）；
  ② 固件控制链（读 `0x8153`→写 `0x83A1`、读 `0x8154`→写 `0x83A2`，再与 SOC `0x847C` 比较 SUbb）；
  ③ ACPI 层**零命中**（说明 XRAM 不经 ACPI OperationRegion）
- `ec_35.bin` 与 `ec_40.bin` 131,073 字节里只差 15 字节 ⇒ **XRAM 布局跨 BIOS 35/40 稳定**
- ⭐ **出厂默认阈值不存在**：固件里只有 `MOV A,#1/#2/#0xEE` 这类控制标志，没有 50/60/80 初值
  ⇒ 基线是「**模式 0 = 不做阈值控制 = 充到 100%**」，回滚靠发 `0x0F` 恢复命令，不是写回原值
- ⚠️ **EC 版本号有矛盾**：实测记录是 `00.21.00.00`、`NATIVE_README.md` 说 `00.28.00.00`、
  脚本 docstring 的支持列表里连 `00.21` 都没有 ⇒ **必须以真机读数为准**

### 核心结论
**键盘灯不走 HID，走 GCU/EC 的 MQTT 通道**：官方每次操作发 `Keyboard/Ctrl` ＋ `function="SetEffectALL"`，
GCU 回的 `Keyboard/Status` **自报 `"solution":"EC"`** ⇒ **最终执行者是 EC**：
```
官方控制台 →（MQTT Keyboard/Ctrl · SetEffectALL）→ GCU →（EC）→ 键盘背光
```
⚠️ **宝龙达没有 GCU** ⇒ 这条转发链**断在中间** ⇒ 需自行复现 GCU 那一步（把指令翻成 EC 操作）。
⭐ payload 里 `powerstatus`（疑为灯的电源状态 ⇒ "关灯"）、`level`（疑为亮度）值得追。

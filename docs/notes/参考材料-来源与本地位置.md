### 关键协议事实（只取事实）
```
端口 0x66 = 状态/命令   端口 0x62 = 数据
读：向 0x66 发 0x92 → 经 0x62 依次传「地址高字节、地址低字节」→ 从 0x62 读数据
写：向 0x66 发 0x93 → 经 0x62 传「地址高字节、地址低字节、数据」

XRAM 地址表：
  0x8150 Mailbox 主命令（写 0x10 触发）    0x83C0 模式
  0x8151 子命令/参数                        0x8370 状态
  0x8152 结果（0x55 = 成功 / 0xAA = 未知子命令）  0x847C SOC
  0x8153 原生阈值上限                       0x8410~0x8413 EC 版本
  0x8154 原生阈值下限                       0x8460 标志位
子命令：0x0D 启用原生阈值 / 0x0E 停充 / 0x0F 恢复
模式值：0x00 正常 / 0x02 停充 / 0x48 原生阈值模式
```
- **地址表三重独立确认**：EC 固件里 `MOV DPTR,#addr` 硬编码（`0x8153` 被引用 42 次）；
  固件控制链（读 `0x8153`→写 `0x83A1`、读 `0x8154`→写 `0x83A2`，再与 SOC `0x847C` 比较）；
  以及 ACPI 层**零命中**（说明 XRAM 不经 ACPI OperationRegion）
- `ec_35.bin` 与 `ec_40.bin` 131,073 字节里只差 15 字节 ⇒ **XRAM 布局跨 BIOS 35/40 稳定**
- ⭐ **出厂默认阈值不存在**：固件里只有 `MOV A,#1/#2/#0xEE` 这类控制标志，没有 50/60/80 初值
  ⇒ 基线是「**模式 0 = 不做阈值控制 = 充到 100%**」，回滚靠发 `0x0F` 恢复命令，不是写回原值

### 已查实的关键结论
- ⛔ **没有充电阈值功能**（88 个类型里零命中 Battery/Charge/Threshold）
- ⛔ **不支持自定义档**：`CLISetPerformaceMode` 只映射 `0/1/2`（`CustomMode=3` 无使用点）
  —— 这是继"蛟龙开源项目服务端枚举只有 0/1/2"之后的**第二个独立确认**

  **只有 Set 没有 Get** ⇒ 印证"功能号 23 只写不读"
- ✅ **键盘灯**：`Models.Keyboard` 只有"设颜色（**必须先写模式 2**）"与"设亮度"，**无关灯操作**

  ```
  读 0x2000 / 0x2001 芯片 ID（期望 0x55）→ 把 0x1060 置 bit7 解锁
  ```
  ⭐ 这是**设计 PawnIO EC 模块时必须包含的一步**
- ✅ 协议层与我们**逐项一致**（`byte[32]`、`[1]=250/251`、`[3]=功能号`、值从 `[4]`、
  `MICommonInterface` + `MiInterface`）；而且官方**把实例名硬编码成 `MIFS_0`**，
  我们做了候选名＋枚举兜底（机器 C 是 `MIFS_0`、机器 B 是 `MIFS`）⇒ **我们比官方更稳**

### 那份分析的核心结论
**键盘灯不走 HID，走 GCU/EC 的 MQTT 通道**：
- 官方每次操作发 `Keyboard/Ctrl` ＋ `function="SetEffectALL"`
- GCU 回的 `Keyboard/Status` **自报 `"solution":"EC"`**、`"type":"SingleZone"`
- ⇒ **最终执行者是 EC**。链路：
  ```
  官方控制台 →（MQTT Keyboard/Ctrl · SetEffectALL）→ GCU →（EC）→ 键盘背光
  ```
- ⚠️ **宝龙达没有 GCU** ⇒ 这条转发链**断在中间** ⇒ 需自行复现 GCU 那一步（把指令翻成 EC 操作）

## 一、⭐⭐ 最关键的发现：功能号 8 的 raw 值**直通，不重映射**

### 30 系的枚举原样

```csharp
public enum WMISystemPerMode : byte {
    BalanceMode     = 0,
    PerformanceMode = 1,
    QuietMode       = 2,
    Unknow          = byte.MaxValue
}
```

### 写：直接把枚举值当 raw 写下去

```csharp
public void SetSP_PerformaceMode(WMISystemPerMode m) {
    LogHelper.WriteLog("SetSP_PerformaceMode", m.ToString());
    Task.Run(() => WMIMethodServices.SetValue(WMIMethodName.SystemPerMode, m));
}
```

`SetValue` 内部：`array[4] = (byte)setvalue;` ⇒ **raw = 枚举值本身**。

⭐ **没有任何"内部值 → raw"的换算。**

### 读：同样直通

```csharp
public static T GetValue<T>(WMIMethodName name) {
    ...
    byte b2 = tuple.Item2[4];      // 取 OutData[4]
    return (T)(object)b2;
}
```

⇒ 读到什么就是什么，**不重映射**。

### ⚠️ 与我们实现的差异（**疑似 bug**）

| 语义 | 我们写出的 raw | 官方 30 系写出的 raw |
|---|---|---|
| 平衡 | **2** | **0** |
| 性能 | **0** | **1** |
| 静音 | **1** | **2** |

我们的映射（`内部0→raw2 / 1→raw0 / 2→raw1`）来自**同方老接口**的约定，
而 **30 系官方是直通**。⇒ **宝龙达机型上这套重映射很可能是错的。**

⚠️ 但这**不能完全解释**"回读失败"：
- 写"性能"（内部 1）→ 我们发 raw 0 ⇒ 30 系理解为 **Balance**
- 回读 raw 0 → 我们映射成内部 1（性能）⇒ **按理应判成功**
- 实际却失败 ⇒ 说明**回读读到的不是 raw 0**（写入被拒？或无响应？）

⇒ **具体 raw 值仍须真机诊断**（`a013beb` 已加诊断会打出未知 raw 值）。
⇒ **改映射是高危动作，须用户拍板**，本文档只报事实。

## 二、⭐ 官方**不做回读校验**

```csharp
public static bool SetValue(WMIMethodName name, object setvalue) {
    bool result = true;
    byte[] array = _MakeMethodPrams(WMIMethodType.Set, name);
    array[4] = (byte)setvalue;
    Tuple<bool, byte[]> tuple = ExcMethod(array);
    if (!tuple.Item1) { result = false; }   // 只看有没有抛异常
    return result;
}
```

⇒ **只判 `ExcMethod` 是否抛异常**，**完全不校验回读值**。
（与 40 系完全一致。）

⇒ 所以"回读失败"是**我们自己的严格判据**造成的，**官方不认为那是失败**。
⇒ 也说明：**若真机确认模式实际生效了，那我们的判据就该放宽，而不是去改 EC 协议**。

## 四、⭐⭐⭐ 30 系的 `WMIMethodName` **只到 18**（40 系到 23）

```csharp
public enum WMIMethodName {
    SystemPerMode = 8, GPUMode = 9, RGBKeyboardStatus = 10, FnLock = 11, TPLock = 12,
    CPUGPUFanSpeed = 13, GPUFanSpeed_NotUse = 14, Ambientlight = 15,
    RGBKeyboardMode = 16, RGBKeyboardColor = 17, RGBKeyboardBrightness = 18,
    UnKnow = 255
}
```

**没有**：`SystemAcType=19`、`MaxFanSpeedSwitch=20`、`MaxFanSpeed=21`、`CPUThermometer=22`、`CPUPower=23`。

40 系那版**有**这五个。

### ⚠️ 但这**不等于固件不支持**
- 30 系那版控制台本身较简单（没有功耗墙 UI）⇒ **可能只是没用到**
- `CPUThermometer` 在 30 系代码里**只是 UI 控件名**（`CPUThermometer.Text = cputemp + "℃"`），
  温度来自它自带的 **`LibreHardwareMonitorLib`** ⇒ **官方用 LHM，不用功能号 22**
- 全量搜 `SystemAcType|MaxFanSpeed|CPUPower` ⇒ **无任何功能号用法**

⇒ **结论**：30 系官方"不需要"19~23，**不能据此判定固件没有**。
⇒ **真机读一次才能定**（白名单修好后 30 系会走宝龙达后端，届时诊断段的 8~23 试读会给出答案）。

## 五、⭐⭐ 「游戏模式」按钮实际写的是 **Balance**

```csharp
FastestMode_Click → SetAP_PerformaceMode(PerformanceMode);  SetSP_PerformaceMode(PerformanceMode);   // raw 1
PlayingMode_Click → SetAP_PerformaceMode(BalanceMode);      SetSP_PerformaceMode(BalanceMode);       // raw 0
WorkMode_Click    → SetAP/SP_PerformaceMode(QuietMode);                                              // raw 2
```

⭐ **按钮名与语义错位**：`PlayingMode`（游戏）→ **`BalanceMode`**。

⇒ **这解释了用户「屁股的灯只有平衡模式才亮」**：
只有 `PlayingMode` 那个按钮发的是 Balance（raw 0），所以只有它触发对应灯效。

### ⚠️ 另一处易误读：`SetAP_PerformaceMode` **不改灯**
```csharp
public void SetAP_PerformaceMode(WMISystemPerMode m) {
    switch (m) {
    case BalanceMode:     WorkMode.IsEnabled = true;  FastestMode.IsEnabled = true;  PlayingMode.IsEnabled = false; break;
    case PerformanceMode: WorkMode.IsEnabled = true;  FastestMode.IsEnabled = false; PlayingMode.IsEnabled = true;  break;
    case QuietMode:       WorkMode.IsEnabled = false; FastestMode.IsEnabled = true;  PlayingMode.IsEnabled = true;  break;
    default: LogHelper.WriteLog("SetAP_PerformaceMode", "Error!!!Get Unknow PerformaceMode"); break;
    }
}
```
⇒ `AP` = **Apply（应用到 UI）**，只改三个按钮的 `IsEnabled`，**与灯无关**。
⇒ 所以**不能拿"A 面灯变色"当作模式切换成功的证据**。

## 八、对我们"回读失败"的结论与建议

### 已排除
- ❌ **帧长度**：30 系严格 32 字节，与我们一致
- ❌ **取值下标**：`[4]`，与我们一致
- ❌ **实例名/方法名**：`MIFS_0` / `MiInterface`，与我们一致

### 已确认的差异
- ⭐ **写 raw 值**：官方**直通**（0/1/2），我们**重映射**（内部0→2 / 1→0 / 2→1）

### 还需真机证据
- 写 `1`/`2` 后**回读到底读到什么 raw**（不在 `{0,1,2,3}` 说明写入被拒或响应异常）

### 建议（**等拍板，不改代码**）
1. ⭐ **宝龙达机型的模式映射改为直通**（`内部值 == raw`），与官方一致；
   ⚠️ 但要先确认"内部值"的定义与我们 `PerfMode` 枚举一致（0=平衡/1=性能/2=静音）
2. ⚠️ **若改直通后仍失败** ⇒ 那不是映射问题，需查"写入是否被 EC 接受"
   （可能 30 系固件对某些 raw 值有额外约束，类似斗战者发现的"模式区间限制"）
3. 💡 **回读判据可考虑放宽**：官方根本不校验；我们可以
   「写成功即视为已下发，回读不一致则**如实标注未确认**而非判失败」——
   这与我们已有的"三层诚实"（写成功/回读一致/需目视）口径一致
4. ⚠️ **不要**据此改动功能号 19~23 的任何逻辑（30 系官方没用 ≠ 固件没有）

### ⭐ 由此得出的**唯一实质差异**

**模式（功能号 8）的 raw 值映射**：
- 官方 30 系 **和** 40 系 **都是直通**（raw == 枚举值）
- **我们是重映射**（来自同方老接口约定）
- ⇒ ⭐ **这个重映射在宝龙达机型上是错的**（两个机型都错，不是"30 系特殊"）

### ⚠️ 但"改直通"仍须先确认两件事
1. **我们的"内部值"定义是否与 `WMISystemPerMode` 对齐**（内部 0=平衡 / 1=性能 / 2=静音？
   —— 需核 `PerfMode` 枚举与 `SwitchMode(int)` 的参数语义）
2. **宝龙达后端走的是否就是这条重映射路径**
   （日志里 `MechrevoService.SwitchMode(...) 老接口后端` 说明它当前走 legacy 那条；
   白名单修好后是否走同一函数、同一重映射，需查代码）

⇒ **这两条确认前不要改**（本文档只报事实，不改代码）。

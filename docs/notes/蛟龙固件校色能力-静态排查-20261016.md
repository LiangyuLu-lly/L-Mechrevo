# 蛟龙（宝龙达）固件层「屏幕校色 / 色彩增强」能力排查

**日期**：2026-10-16
**材料**：`_upstream\JiaoLong16Pro-Battery-threshold\JiaoLong16Pro-Battery-threshold-main.zip`
（宝龙达模具自己的原始固件材料，非第三方项目代码）
**方法**：纯静态分析、只读。未解压进仓库（用 `%TEMP%` 临时目录，用后清理）、未碰 EC、未写任何寄存器。

## 一、结论

**宝龙达（蛟龙 MRID6）在固件/硬件层【没有】屏幕校色或色彩增强能力。**

五层独立排查，全部零命中，且**检索方法经过对照验证**（见第三节）。
⇒ 意味着现有实现（**只能走 Windows 标准 API 的 ICC 关联**）**是正确的**，
"保留「自定义 ICC」＋「设置」入口、隐藏 GCU 开关"这个取舍无需改动。

⚠️ 注意：这与"官方控制台能不能做"无关 —— 那是另一回事（宝龙达官方控制台 `JiaoLong7.3`
反编译也没有校色功能，已有独立结论）。这里回答的是**固件/硬件到底有没有**。

## 二、五层证据

### 第 1 层：ACPI（`dsdt.dsl` + 38 个 SSDT/其它 `.dsl`，合计 1,870,427 B）

搜 `ColorCalibration` / `ColorCalib` / `Calibration` / `Calibrate` / `DisplayEffect` / `Vivid` /
`Saturation` / `ColorTemp` / `ColorTemperature` / `ColorEnhance` / `色温` / `校色` / `色彩`
⇒ **全部零命中**。

存在的**只有标准显示接口**（与校色无关）：
| 位置 | 内容 | 性质 |
|---|---|---|
| `dsdt.dsl:3460` | `_DOD` Display Output Devices | 标准 ACPI，枚举显示输出 |
| `dsdt.dsl:3531` | `_BCL` Brightness Control Levels | 标准 ACPI，背光档位 |
| `dsdt.dsl:3537` | `_DDC` Display Data Current | 标准 ACPI，**只读 EDID** |
| `dsdt.dsl:3549` | `_BCM` Brightness Control Method | 标准 ACPI，背光 |
| `ssdt4.dsl:210` | `NBCI_FUNC_GETBACKLIGHT` | 厂商背光读取（仍是背光） |
| `ssdt7.dsl:812` | `Panel Brightness Backlight Level` | ATIF（AMD）背光 |
| `ssdt4.dsl` | `Name (ACBT, 0x50)` | 背光相关常量 |

⇒ 有**背光亮度**（`_BCL`/`_BCM`），**没有色彩/色温/Gamma**。

### 第 2 层：EC 固件（`ec_35.bin` / `ec_40.bin`，各 131,073 B）

**（a）没有 Gamma/LUT 表**：全文件扫"单调递增的 256 字节表"（Gamma LUT 的典型特征，要求单调且递增步数 > 200）⇒ **命中 0**。

**（b）命令面完整解码后，没有任何显示/色彩功能**。EC 的 WMI mailbox 是**两级分派**：

- `0x8150` = 主命令（函数号）
- `0x8151` = 子命令
- `0x8152` = 结果（`0x55` = 成功，`0xAA` = 未知子命令）
- 分派例程：`LCALL 0x7A4A`，后接 `(目标地址16, 键8)` 三元组表，`00 00` 终止

**主命令表**（`ec_35.bin @0x4B08`）：

| 主命令 | 处理体 | 子命令表 | 触及的 XRAM | 判定 |
|---|---|---|---|---|
| `0x01` | `0x4B27` | — | — | 版本/信息类 |
| `0x02` | `0x4B2F` | — | 写 `0x8155` | 参数写 |
| **`0x10`** | `0x4B3B` → `0x4540` | **表A（21 项，`0x01`–`0x15`）** | `0x8153/0x8154`、`0x83A1/0x83A2`、`0x83C0`、`0x8460`、`0x848E`、`0x8902`–`0x8953` | **电池/充电组**（限充项目用的就是它：`0x10` + 子命令 `0x0D/0x0E/0x0F`） |
| `0x20` | `0x4B40` → `0x472D` | 表B（12 项） | `0x8417`–`0x841F`、`0x8153`–`0x815B`、`0x8830`–`0x883F`、`0x84E4`、`0x8199`、`0x83C1` | 参数块搬运 |
| `0x30` | `0x4B45` → `0x4826` | 内联 | `0x8420`、`0x8153`、`0x83C1`、`0x8199`、`0x8820/0x8821` | 开关类 |
| `0x40` | `0x4B4A` → `0x486D` | 表C（9 项） | `0x83BC`、`0x83C1`、`0x83F6`、`0x84E8`–`0x84EB`、`0x819D/0x819E`、`0x81B6` | 参数组 |
| `0x50` | `0x4B4F` → `0x4905` | 内联 | 从 `0x91A2`/`0x91A4`/`0x9040`–`0x9043` 复制到 `0x8153`–`0x8156` | 块复制 |
| `0x60` | `0x4B54` → `0x494D` | 内联 | `0x8420`、`0x83C1`、`0x8153` | 开关类 |
| `0xF0` | `0x4B59` → `0x498B` | 表D（17 项） | `0x8410/0x8411`（**EC 版本**）、`0x8307`、`0x8315`、`0x83BB`、`0x83C0/0x83C1`、`0x83C8/0x83C9`、`0x8421`、`0x8820/0x8821`、`0x883C`–`0x883F`、`0x89E2/0x89E3`、`0x8199` | 信息/状态组（子命令 `0x01` 读 EC 版本） |

**涉及的全部 XRAM 地址**都在 `0x81xx`（主机接口/mailbox 参数）、`0x83xx`（状态）、
`0x84xx`、`0x88xx`、`0x89xx`、`0x90xx`、`0x91xx` —— 与**电池电量计、热管理、风扇、系统状态**一致，
**没有任何显示/面板/色彩块**。

**（c）色温类常量不可信**：搜大端 16 位 `6500/9300/2700/5000/5500/7500/4000/4500/6000/7000/8000/10000`
只得到零星命中（`6000`×5、`8000`×2，其余 ×1）。
但 **131,073 字节对任一 16 位值的随机期望命中 ≈ 2.00 次** ⇒ 这些是**噪声**，不构成证据。

### 第 3 层：BIOS 镜像（`BIOSv35.bin`，35,576,920 B）

ASCII（Latin1 视图）＋ UTF-16LE（**双对齐**）搜：
`ColorCalibration` / `ColorCalib` / `Calibration` / `Calibrate` / `DisplayEffect` / `ColorEnhance` /
`ICCProfile` / `ColorProfile` / `Gamma` / `ColorTemp` / `Saturation` / `Vivid` / `Color` /
`Backlight` / `Brightness`
⇒ **全部 x0**（唯一的 `Hue` ×2 是随机字节里的 `HuE` 假命中）

**对照测试（证明方法有效，不是假否定）** —— 同一镜像里能正常找到通用字符串：
```
Version x107   Battery x15   Display x18   Boot x14   CPU x11   Save x10
Advanced x6    Power x5      Security x5   Exit x3    Keyboard x2
Setup x0       Fan x0        Panel x0      Color x0   Gamma x0   Brightness x0   Calibration x0
```
⇒ BIOS 里有明文设置项字符串，而**色彩相关的确实一个都没有**。

⚠️ 保留意见：BIOS 设置数据可能部分压缩（`Setup`/`Fan`/`Panel` 也是 x0 提示这一点）。
所以"BIOS 无色彩设置项"的强度**低于** ACPI 与 EC 两层的结论；但三层加起来已足够。

## 三、方法论（含一个会坑人的 bug）

1. ⚠️ **PowerShell 的 `-shl` 对 `[byte]` 会截断**：`[byte]0x81 -shl 8` 得到 **0**，不是 `0x8100`。
   我第一次扫 EC 的 `MOV DPTR,#imm16`（`90 hi lo`）时因此得到"`0x8000`–`0x8FFF` 零命中"的**假否定**，
   与既有的"`0x8153` 被引用 42 次"直接矛盾才暴露出来。
   **正确写法**：`($b[$i+1] * 256) + $b[$i+2]`。以后写 EC 分析脚本务必注意。
2. **大文件字符串检索不要用逐字节循环**（35 MB × 多个关键词会跑到超时、被迫转后台）。
   用 `Encoding.GetEncoding(28591).GetString(bytes)` 建 Latin1 视图 ＋ `String.IndexOf`，
   UTF-16 则要**做两个偏移（0 和 1）**否则会漏掉奇数对齐。
3. **负结论必须配对照测试**：先确认"应该存在的字符串找得到"，再说"目标字符串找不到"。
   本次 BIOS 那层做了（见第 3 层），PawnIO 模块那次也做过（同批 `IntelMSR.bin` 哈希自证）。
4. **16 位常量命中要算随机基线**：131 KB 对任一 16 位值期望 ≈ 2 次，命中 1–2 次无意义。

## 四、附带发现（对其它任务有用）

### 1. `AOD` 是宝龙达上**另一个** `PNP0C14` WMI 设备（`ssdt10.dsl:1369`）
```asl
Device (AOD) {
    Name (_HID, EisaId ("PNP0C14"))   // Windows Management Instrumentation Device
    Name (_UID, "AOD")
    Method (AM01..AM09)               // 经 WMAA 分派
    Name (_WDG, ...)                  // 两个 GUID
}
```
- `AM01` 返回 `\AODV`；`AM02` 置 `GF01=1`；`AM03` 返回 `\OBID`
- `AM04(Arg0)` / `AM06(Arg0)` 按 `\OBIT` 表查项，返回 0x19C / 0x14 缓冲
- **`AM05(Arg0)` 走 SMI**：`SCMI=DCMI; SCMD=DCMD; ASMO=DSMI`（`OperationRegion (PSMI, SystemIO, ASMI, 2)`，即 APM/PSMI 端口）
- `AM07(Arg0)` 返回 `DSPD` 表第 `Arg0` 项（每项 `0x214`=532 B，最多 16 项）
- `AM09` 返回 `RMPD`（0x8C B）
⇒ 看起来是**厂商通用表/阈值访问**接口，**未发现显示/色彩用途**，但它是一个我们**尚未使用过**的 WMI 接口，
  值得留档（将来若要找"厂商还暴露了什么"可从它入手）。

### 2. EC mailbox 是**由 SMM 驱动**的，不经 ACPI
DSDT/SSDT 里搜 `0x8150`–`0x8154`/`0x83C0`/`0x847C`/`0x8370`/`0x83A0`–`0x83A2` ⇒ **零命中**（既有结论）。
本次找到机制解释：`AOD.AM05` 通过 **PSMI 端口 `0xB0`** 触发 SMI ⇒ 真正的 mailbox 访问在 **SMM 代码**里。
⇒ 所以想在 ACPI 层找 EC 功能号是找不到的，**必须直接分析 EC 固件**（本文档第 2 层）。

### 3. 宝龙达存在**三套** EC 地址空间（别混用）
| 通道 | 端口 | 地址示例 | 来源 |
|---|---|---|---|
| ACPI EC（标准） | `0x62` 数据 / `0x66` 命令（命令 `0x92` 读 / `0x93` 写） | XRAM `0x8150` mailbox；EC RAM `0x9A`（斗战者的键盘背光等级） | 限充项目、斗战者 |
| Jiaolong 开源 | `0x4E` 地址 / `0x4F` 数据 | `0xC411`（EC 版本）、`0xC834`/`0xC835`（风扇 RPM）、`0xC836`/`0xC837`（档位）、`0xC83C`/`0xC83D`（转速设定） | `SysEnums.ECMemoryTable` |
| 官方控制台 7.3 | `0x2E` / `0x2F` ＋ 命令 `0x11`，`ushort` 16 位索引 | 任意 XRAM（含 `0x81xx`）；需 `Write_EC_Init()` 解锁前置 | 反编译 `第三方蛟龙游戏控制中心.dll` |
⚠️ `ECMemoryTable` 里 `0xC411`/`0xC83x` 这套**不在** `0x81xx`/`0x84xx` 里 —— 是第三个地址段。

### 4. EC 命令表可直接复用（将来做键盘背光/风扇时省一次逆向）
本文档第二节（b）的表就是完整的 `(主命令, 子命令) → 处理体` 映射。
已知锚点校验：`0x10` + `0x0D/0x0E/0x0F` = 充电阈值（与限充项目一致）✅；
`0xF0` + `0x01` 读 `0x8410/0x8411` = EC 版本 ✅（与我们诊断段读 `0x8410`–`0x8413` 一致）。

### 5. EC 版本号矛盾再获一份佐证
`ec_35.bin` 与 `ec_40.bin` **131,073 B 里只差 15 字节**，其中 `0x08036`/`0x08040`/`0x0804F`–`0x08052`
那几处像 ASCII 版本串（`33`→`38`、`23`→`28`、`31 31 30`→`38 30 32`）——
与"实测 `00.21` / README 称 `00.28`"的矛盾一致，**再次说明版本校验必须以真机读数为准**。

## 五、对现有实现的意义

| 部分 | 通道 | 宝龙达 | 结论 |
|---|---|---|---|
| 自定义 ICC | `IccHelper` → `WcsAssociateColorProfileWithDevice`（Windows 标准 API / mscms.dll） | ✅ 能用 | **保留** |
| 预设档位 + GCU 开关 | GCU 上报 + `SetColorCalibration`（MQTT） | ⛔ 不能用 | **隐藏** |

⇒ 固件层没有可挖掘的能力，**现有方案（纯软件 ICC）不是妥协，而是唯一可行路径**。
不必再往固件方向投入。（同方模具那两个 `ControlCenter` 包与本结论无关，模具不同，用户已明确"没意义"。）

# 后端匹配：声明式架构目标（机型先行 → 路由）

> 机主口径（2026-10-20）：**后端匹配最后要做到声明式架构 —— 先验机型，再选择走哪路。**

## 1. 目标形态（两层）

### 第一层：机型识别（只做事实采集，不做路由）

输出一个只读的 `MachineIdentity` 事实集，每个事实都**带来源**（可审计）：

| 事实 | 来源（示例） | 用途 |
|---|---|---|
| 板号 `board` | `reg.BaseBoardProduct` / WMI `Win32_BaseBoard.Product` | 宝龙达白名单（MRID6 / MRID6-*） |
| 机型名 `model` | `Win32_ComputerSystem.Model` / `SystemProductName` | WJXY 关键字（XINGYAO/LNL）、显示 |
| 显卡代际 `gen` | 设备名 / 驱动 | 30/40/50 分流、能力位 |
| GCU 服务是否安装 `gcuInstalled` | 服务注册表键 / ItemSupport 快照 | 决定是否候选 GCU |
| `MICommonInterface` 是否存在 `mifsClass` | `root\WMI:MICommonInterface` | 宝龙达/老同方的共同前提 |
| 项目号 `projectId` | GCU 上报 / BIOS | 机型细分 |
| 无界 APU `wujieApu` | SMU 探测 | 无界分支 |
| AMI/AMD 平台等 | WMI/驱动 | 能力位 |

约束：

- 每个探针**只读**、有超时、失败= `Unknown`（不猜、不抛）；
- 识别结果**与后端无关**：同一台机器在任何后端下识别结果一致；
- ⛔ 不允许“探测失败 ⇒ 换个后端再试”式的隐式路由。

### 第二层：路由（声明式规则表）

路由 = 一张**有序规则表**，每条规则 = 条件（对 `MachineIdentity` 的谓词）+ 后端 + 说明；首条命中即选中，未命中落到兜底规则。

```text
规则示例（目标形态）
1. when board ∈ 宝龙达白名单                  → BaoLongDa
2. when gen == Gen30/40/50 && gcuInstalled     → Gcu
3. when gcuInstalled                           → Gcu
4. when mifsClass && !gcuInstalled             → LegacyMifs
5. fallback                                    → Gcu（未连接则如实提示）
```

要求：

1. **规则是数据/声明**，不是散落在 `if/else`/lambda 里的隐式顺序；
2. 每次路由产出一行日志：`backend=… | machine=… | rule=#n | facts=…`（可解释、可对比诊断包）；
3. 新增机型/后端 = **加一条规则或一个探针**，不改控制流；
4. 明确「机型优先于服务存在性」：机型能证明属于某分支时，不许被“恰好装了某服务”抢走。

## 2. 为什么现在要这么做（已踩过的坑）

- `MechrevoBackendOrder.Candidates` 当前是**命令式候选表**：GCU 在第一位且判据仅为“装了 GCU 服务”；
- 蛟龙（宝龙达，`MRID6-23`）同时也装了 GCU 服务 ⇒ GCU 抢先 ⇒ `UsesBaolongda=False`、显示「GCU 未连接」，白名单明明命中却没生效；
- 同类风险：50 系同方若残留 GCU 服务、30 系宝龙达与 40 系宝龙达板号变体、WJXY 与 50 系判据交错。

临时修复（已提交）：GCU 候选加“白名单未命中”条件，让宝龙达先被选中。**这只是补丁，不是目标形态**。

## 3. 迁移步骤（建议顺序）

1. **抽 `MachineIdentity`**：把现有分散的板号/机型/代际/GCU 服务/MIFS 探测收成一处，只读、带来源、带 Unknown；
2. **路由表数据化**：用规则表替换 `Candidates` 的顺序语义（后端探测仍保留“返回 null = 不可用”，但**顺序由规则决定**）；
3. **后端声明能力**：每个后端声明“需要哪些事实 + 支持哪些机型类别”，由路由统一判断；
4. **日志/诊断对齐**：`[gate] 机型分类` 与路由日志共用同一份 `MachineIdentity`，避免静态诊断与运行判定不一致（本次蛟龙现象就是两套判据不一致）；
5. **验收口径**：每个机型一条可复现的路由日志；诊断包的「白名单/GCU/MIFS」段与运行日志必须一致。

## 4. 边界与纪律

- 先验机型：**任何路由选择都必须能引用机型事实**，不允许“先试某后端、失败再换”；
- 宁可不认宝龙达，也绝不误伤同方（白名单硬闸门保留）；
- 改动只碰后端选择/识别层，不动各后端内部协议实现；
- 诊断包与日志格式保持向后兼容（新增字段不删旧字段）。

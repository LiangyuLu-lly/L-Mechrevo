## 二、事实：我们发了什么

EC 端口 I/O 只用两个端口：

- `0x66` = 状态/命令；`0x62` = 数据
- 写入 0x66 的命令字节**只有** `0x92`（厂商读）与 `0x80`（ACPI 标准读）
- 写入 0x62 的只有**地址高/低字节**
- **从未发送** `0x93`（厂商写）/ `0x81`（ACPI 写），**从未向 0x62 写数据字节**

所以不是"写 EC 写坏了"，但"发命令 + 连续访问"本身有风险。

## 三、推断原因

1. `0x92` 是**厂商自定义读命令**（16 位地址），ACPI 规范里没有；其语义/时序只在特定 EC 固件上核对过。
2. 4KB 全片读取 = 4096 次事务 × 每字节 5~6 次端口 I/O，且是**忙等无间隔**循环。
3. ACPI EC 端口是全局共享资源（BIOS/EC 自身也在用），高频抢占总线可能导致 EC 与主机失步、EC 看门狗触发或固件异常 ⇒ 硬件复位。

> 同一条通道（PawnIO `LpcACPIEC`）在 LM 里只用于**小范围、带超时、失败即停**的诊断读取，未做过 4KB 连续扫描。

## 四、安全规则（已落实到代码）

1. **日常机禁止端口 I/O 探测**。需要 0x700–0x7FF 的数据，继续用 `\\.\ACPIDriver` 通道（内核驱动、单次调用、快且稳）。
2. 探针的本机端口通道**默认禁用**：
   - 必须 `-EnableLocalPortIo -IUnderstandRisk` 双开关
   - 单次最多 64 个地址
   - 只用 ACPI 标准读 `0x80`（已删除 `0x92`）
   - 每次读取强制 5ms 间隔，任一步失败立即停止
3. 代理 `/ecdump` 同步收紧：单次最多 512 个地址、只用 `0x80`、每次 2ms 间隔。
4. 需要"全片 EC"时：优先在**测试机**上做，或从 BIOS/EC 固件离线取（用文档里的字节模式判据），不要在主力机连续扫描。

## 五、ACPI 能读多少 EC？

- ACPI EC 接口（0x62/0x66 + 0x80/0x81）只覆盖 **8 位地址空间：0x00–0xFF（256 字节）**。
- 0x100 以上的 EC RAM（如 0x700–0x7FF 的 H2RAM、0x800+ 的 XRAM）必须靠**厂商扩展**：
  - 厂商分页/窗口机制（同方的 `\\.\ACPIDriver` 就是 H2RAM 0x700–0x7FF 的窗口镜像）；
  - 厂商 16 位地址命令（`0x92/0x93` 这一类）；
  - 或直接读 EC 固件文件（离线）。
- 所以"用 ACPI 读全部 EC"做不到；能做到的只是 256B + 厂商窗口。

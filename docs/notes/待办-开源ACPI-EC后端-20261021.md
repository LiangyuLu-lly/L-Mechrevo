# 待办：GCU 机型接「开源 ACPI EC 控制后端」（2026-10-21 记录，未开工）

> 机主原话（2026-10-21）：「如果我到时候给 GCU 机器接开源的 ACPI EC 控制后端，能比较方便切换吗」→ 结论可行，先记录，暂不实现。

## 目标

给 GCU 机型（同方 30/40/50、WJXY/星耀等）增加一个**可切换的开源 ACPI EC 控制后端**（经 PawnIO `LpcACPIEC` 0x62/0x66 或其它开源 EC 通道），与现有 GCU 后端并存，按声明式路由选择，便于对比/回退。

## 当前可复用的骨架

- `MechrevoBackendKind` 枚举 + `MechrevoBackendOrder.Candidates`（探测委托，非 null 即可用）；
- `BackendRouter`：有序声明式规则表 + 后端能力声明（`BackendDeclaration`，含 RequiresFacts / Supports）；
- `MachineIdentity`：板号/机型/代际/GCU 服务/MIFS 等只读事实；
- 运行日志统一为 `[强化机型分流] backend=… | machine=… | rule=#n … | decl=…`；诊断包有 `[强化机型分流（只读）]` 一节。

## 接入步骤（建议，未开始）

1. **骨架 + 只读**：`AcpiEc = 4` 枚举值 + `AcpiEcBackend.TryCreate()`（能打开 EC 通道并读到身份才返回非 null）+ 路由规则 + 能力声明；只读字段写日志，不写硬件。
2. **字段逐个接管**：先温度墙/PL1/PL2（带回读确认），再风扇曲线；每字段独立开关，避免“整个后端一刀切”。
3. **切换方式**：配置项 `backend_prefer = gcu / auto / acpiEc`（默认 gcu/auto）；`auto` 仅在 GCU 不可用时用 ACPI EC。
4. **验收**：每台机型一条可复现路由日志；诊断包与运行日志一致；写入失败如实显示（⛔ 不假装生效）。

## 必须遵守（无界/宝龙达踩过的坑）

- **单一写者**：GCU 服务与 ACPI EC 同时写同一字段会互相覆盖 ⇒ 字段级声明“谁写谁只读”，或仅 GCU 让位时启用 EC。
- **先只读后写入**：每字段先探针、再小步写、再回读；不全量放开。
- **能力驱动 UI**：能力位未确认时 UI 不显示可调行（避免“能改但不生效”）。
- **路由可解释**：命中哪条规则、用了哪些事实都要落日志；⛔ 不做“探测失败换后端”。

## 工作量估算

- 路由 + 骨架 + 只读：约 1 天；
- 第一批字段（温度墙/PL）写入 + 真机验证：1–2 天；
- 风扇曲线等复杂字段：按机型逐个来。

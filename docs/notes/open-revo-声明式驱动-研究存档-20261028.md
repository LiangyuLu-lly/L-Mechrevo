## 一、声明式驱动是什么

open-revo 不是“每个机型写一份驱动”，而是：

```text
JSON 机型清单（ModelManifest）
  → 通用 HAL 解析
  → 选择 Channel
  → 执行 Action
  → Guardrail 限权
```

新机型理论上只增加 JSON，不改 Rust 核心。

核心目录：

```text
src-tauri/crates/openrevo-core/src/hal/declarative/
  mod.rs
  driver.rs
  model_manifest.rs
  wmi_mailbox.rs
```

## 三、匹配与执行顺序

```text
1. 外部驱动插件
   %APPDATA%\OpenRevo\plugins\drivers\*.json
2. 内置驱动
   xingyao_14_p916f.json
   wujie_14_ip3.json
   wujie_14_bld.json
   wujie_x_series.json
   jiaolong_16_bld.json
3. 匹配后缓存
4. HAL 选用 DeclarativeHardwareDriver
5. 按 manifest.channels/actions 执行
```

`DeclarativeHardwareDriver` 实现统一的 `MechrevoHardwareHAL`：

```text
set_performance_mode
set_battery_health
set_fan_boost
...
```

## 四、第二层“契约”

`system/model_engine.rs` 还有机器主权契约：

```text
GpuMuxContract
LightingContract
CommunicationBusContract
TakeoverContract
```

这些描述：

```text
机器实际支持什么
GPU MUX 怎么切
灯光后端
通信总线
是否接管官方控制中心
```

用于约束上层 UI 和功能边界。

LM 当前是命令式后端：

```text

```

open-revo 可借鉴为：

```text

```

不建议直接复制 Rust 实现。

## 六、与 NUC/PL4 直接相关的 open-revo 数据

### EC 地址

```text
自定义档：
  PL1        1923
  PL2        1924
  PL4        1925
  TCC        1926
  Custom标志 1798（65 = 开）
  Fan ramp   1927

内置档默认 PL4：
  办公/静音  1846
  平衡       1842
  狂暴       1961

GPU 相关：
  DB_CTRL1   1859
  TGP_OFFSET 1860
  DB_FLAG1   1861
  DB_WATTS1  1862
  DB_CTRL2   1988
  DB_FLAG2   2004
  DB_WATTS2  2005
```

### ACPIDriver 通道

```text
设备：\\.\ACPIDriver
IOCTL_ECREAD  = 0x9C40A488
IOCTL_ECWRITE = 0x9C40A48C
```

写入输入：

```text
写：4 字节地址 + 4 字节值，共 8 字节
读：4 字节地址
```

### PL4 安全规则

```text
PL4 >= PL2 + 20
PL4 <= 250（源码部分位置用 255）
PL1 <= PL2
```

避免 PL4 太接近 PL2 导致 VRM 瞬态保护、CPU 锁低频。

## 九、合规注意


若复制代码：

```text

提供完整对应源码

```

## 十、风险

```text
Manifest 只能表达固定字节和简单解析
PL4 >= PL2+20 这类条件 clamp 需要 C# guardrail
GPU full-power / 非 full-power 分支不能只靠 JSON
风扇曲线整表写入复杂度高
ACPI/WMI 地址因机型/固件不同，不能跨机型直接套
```

## 十一、结论

```text
open-revo 的声明式驱动适合做“机型能力/通道/动作”的抽象层，
不适合直接替代 LM 全部后端。
建议先做只读 manifest + Channel 抽象，
再迁移 NUC/UMI 的 PL 和模式写入，
GPU/风扇曲线最后做。
```

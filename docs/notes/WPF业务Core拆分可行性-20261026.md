## 1. 做法（csproj 设计）

- **显式 SDK 导入**（`<Import Sdk.props/Sdk.targets>`）+ 在导入前设置隔离目录：
  ```xml
  <BaseIntermediateOutputPath>obj\MechrevoLite.Core\</BaseIntermediateOutputPath>
  <MSBuildProjectExtensionsPath>$(MSBuildProjectDirectory)\obj\MechrevoLite.Core\</MSBuildProjectExtensionsPath>
  <BaseOutputPath>bin\MechrevoLite.Core\</BaseOutputPath>
  ```
  原因：Core csproj 与旧工程**同目录**；默认会共用 `source\obj\project.assets.json`，并行/交替构建会互相覆盖。实测隔离后旧工程 `source\obj\project.assets.json` 的 mtime **未变化**。
- `EnableDefaultCompileItems=false` + `EnableDefaultItems=false`：⛔ 不自动吃 `source/**/*.cs`（否则旧 UI 目录也会被编进来）。
- 目标框架/平台/语言版本/`UseWindowsForms=true`/8 个第三方 HintPath **与旧工程完全一致**，避免把"框架差异"误判成"拆分阻塞"。
- 显式 Include：12 个业务目录（`PawnIO` + `MechrevoLite.Battery/.Diagnostics/.Display/.Fan/.Gpu/.Gpu.NVidia/.Hardware/.Helpers/.Mode/.Update/.Usage`）+ 业务根文件（`Logger/CrashRingBuffer/Native*/NvmlHelper/NvidiaSmi/StartupTaskPlan/AmdDisplay` + 反编译辅助集合类型）+ 旧根目录里被业务引用的非窗体文件（`AppConfig.cs`、`AsusFan.cs`、`HardwareControl.cs`、`ScreenGateProbe.cs`）+ `Strings.cs` + 中立 `Strings.resx`（LogicalName 显式指定）。
- 剔除 5 个**纯旧 UI 形态**文件（否则声明期就报缺 `MechrevoLite.UI`）：
  `MechrevoLite.Helpers\DonateControl.cs`、`MechrevoLite.Helpers\ToastForm.cs`、`MechrevoLite.Update\UpdateForm.cs`、`MechrevoLite.Gpu\GPUModeControl.cs`、`MechrevoLite.Mode\ModeControl.cs`。

### 3.4 根因（三类）
1. **`Program` 静态 UI 门面（主阻塞，75 处）**
   - 业务代码直接访问旧 WinForms 入口类的静态状态/动作：`Program.hw`（73）、`Program.acpi`（21）、`Program.UiAuditMode`（10）、`Program.settingsForm`（9）、`Program.ReleaseVersion`（8）、`Program.toast`（6）、`Program.cs`（4，`Program.cs` 字段/静态属性）、`Program.service`（4）、`Program.modeControl`（3）、`Program.PerformanceKey()`（3）、`Program.ReleaseLabel`（3）、`Program.currentSource`（2），以及 `RequestShutdownForUpdate` / `ScheduleGpuOcShutdownGuard` / `SetExternalLightingPowerAsync` / `SetAutoModes` / `StopVendorLightingIdleMonitorForBaolongda` / `RestoreKeyboardLightingAsync` / `PowerSource` / `SuspendLightingTemporarilyAsync` / `SyncKbPowerFromHardwareIfDiverged` 各 1。
   - ⚠️ **绑定歧义实测**：`Probe.dll`（`lm_pkg_files\{app}`，旧工具/测试程序集）的**全局命名空间**里有一个 `internal Program`；引用 Probe 后，`Program` 被解析成这个不可访问类型 ⇒ 报 **CS0122"不可访问"** 而不是 CS0103"找不到"。临时移除 Probe 引用后 CS0122 消失（同时出现 `Probe` 命名空间缺失，说明 Probe 本身也是 Core 依赖）。⇒ Core 正式化前必须二选一：给 Probe 引用加 `<Aliases>` 并在代码 `extern alias`；或把 Core 的状态类改名（推荐 `AppState`）并全局替换 `Program.`。
2. **业务直接调用旧 WinForms 窗体 / UI 控件（CS0103/CS0246/CS0234 共 44）**
   - `ToastForm`（12）、`SettingsForm`（4+4）、`LightForm`（2）、`CustomModeForm`（2）、`ModeControl`（24：命名空间+符号）。
   - 其中 `ModeControl.cs` 是"业务但强 UI 耦合"的协调器（被 Hardware/Diagnostics 等引用），需要拆成 Core 纯逻辑 + UI 壳，不能简单删除。
3. **`MechrevoLite.UI` 命名空间依赖**：已通过剔除 5 个纯 UI 文件从 Core 中移除；`MechrevoLite.Helpers`/`Update` 里仍有个别 UI 类型引用（本次已在剔除范围内，后续重构时一并抽接口）。

## 4. 最小拆分步骤（推荐顺序）

> 目标态：`MechrevoLite.Core`（业务，无旧 WinForms 窗体）；旧 `L-Mechrevo` 只保留 WinForms UI 并引用 Core；WPF 引用 Core。旧 UI 最终可删。

**Phase 0（本任务）**：骨架 + 边界测量。✅ 已完成。
- 需要 Lead 决策：Core 是否允许保留 `UseWindowsForms=true`（若要求"纯业务、无 WinForms"，Phase 1 后仍需处理 60+ 个 `System.Drawing`/WinForms 引用），或拆成 `Core` + `Core.Windows` 两层。

**Phase 1（低风险，约 0.5~1 人日）**：移动"已证明可编"的业务基础设施进 Core（⛔ 本任务不允许改文件，只记录）：
- `AppConfig.cs`、`AsusFan.cs`、`HardwareControl.cs`、`ScreenGateProbe.cs`、`Logger.cs`、`CrashRingBuffer.cs`、`NativeDriverGuard.cs`、`NativeMethods.cs`、`NvmlHelper.cs`、`NvidiaSmi.cs`、`StartupTaskPlan.cs`、`AmdDisplay.cs`、`PawnIO/**`、`Strings.cs`/`Strings.resx`（旧工程改 `ProjectReference` Core，先保留 `Program`/UI 文件）。
- 注意：`AppConfig` 被大量 UI 文件使用，移动后旧工程需引用 Core；避免出现两份 `AppConfig`（会出 `CS0433/CS0104` 歧义）。

**Phase 2（核心重构，约 1~2 人日）**：`Program` 门面 → Core 的 `AppState` + `IUiHost`
- Core 新增静态 `AppState`：`Hw`、`Service`、`Acpi`、`UiAuditMode`、`ReleaseVersion`、`ReleaseLabel`、`PerformanceKey()`、`PowerSource`、`currentSource` 等**纯状态/纯计算**。
- UI 专属动作（`toast`、`settingsForm`、`modeControl`、`RequestShutdownForUpdate`、灯效相关 8 个成员）抽成 `IUiHost`（默认 no-op 实现），旧 Program 实现并注册；业务改调 `AppState.Ui.*`。
- 同步把业务代码里 `Program.` 批量替换为 `AppState.`（22 个成员、约 120 处引用）。
- 解决 `Probe.dll` 全局 `internal Program` 的绑定歧义（改名为 `AppState` 后自然消失；若保留 `Program` 名则给 Probe 引用加 `<Aliases>`）。

**Phase 3（UI 解耦，约 2~3 人日）**
- `ToastForm` → `IToastService`（Core 只发通知，UI 实现）；`SettingsForm` → `ISettingsWindowHost`（查询/回调）；`LightForm`/`CustomModeForm`/`FanCurveForm`/`FirstRunGuideForm` 从业务调用点移除（事件/命令/回调）。
- `ModeControl` 拆为 Core `ModeCoordinator`（纯逻辑，接收 `AppState.Hw`/`Service`）+ UI 壳（保留在旧 UI，向 Core 订阅事件）。
- `MechrevoLite.UI`（RForm/RButton 等 30 个文件）只允许 UI 程序集引用；`Helpers`/`Update` 中若仍引用，抽接口或条件编译到 UI。

**Phase 4（切换验收）**
- `tools/dev/wpf-p0/WpfP0.csproj` 的 `ProjectReference` 由 `L-Mechrevo.csproj` 改为 `MechrevoLite.Core.csproj`；旧 WinForms 工程保留 `ProjectReference` Core 作过渡。
- 验收：`dotnet build MechrevoLite.Core.csproj` **0 错误**（建议同时 0 新警告）；WPF 0 错误；旧工程 0 错误。

## 5. 风险与未确认

1. **同目录双项目 obj/bin 冲突**：已用显式 SDK 导入 + 隔离目录解决（实测旧工程 `project.assets.json` mtime 未变）。若将来把 Core 移到独立目录（如 `source/core/`）则更干净；也可用 `Directory.Build.props` 统一隔离。
2. **`Probe.dll` 的全局 `internal Program`**：已实测导致 `Program` 绑定成"不可访问"（CS0122）。Phase 2 必须消除（改名 `AppState` 最稳；为 Probe 加 alias 也行）。
3. **`Strings` 本地化**：Core 当前只嵌入中立 `Strings.resx`；迁移时要把 `zh-CN` 也做成 Core 的卫星程序集（旧工程已有该 resx，只需复制/改 EmbeddedResource culture 配置）。
4. **`UseWindowsForms=true` 的取舍**：业务层 60+ 文件引用 `System.Drawing`/WinForms（`Color`/`Font`/`Application` 等）。若要求 Core 纯无 UI，需要新增 `Core.Windows` 抽象层或把这些换成基础类型（工作量另估，未包含在 Phase 1~4 里）。
5. **回归风险**：`Program` 门面替换涉及约 120 处调用点 + `UiAuditMode`/审计截图路径；必须逐文件 diff + 旧 WinForms 全量回归（本任务只做编译可行性，不涉及运行验证）。
6. **未验证**：Phase 1~4 均未实施（本任务禁止改源码），实际工作量以 Phase 1 试点（先移 `AppConfig` + `PawnIO`）后的均值外推。

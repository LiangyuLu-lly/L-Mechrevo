# 宝龙达后端「全部接入 + 正确 UI」实施方案（2026-10-16 定稿）

> ⭐ 目标（用户 2026-10-16 原话）：「⭐ **全部接入** 然后我们也要为宝龙达显示**正确的 UI 和选项**
> ⭐ 同时**又不影响同方**的」
> ⭐ 现状：⭐ 性能档 ✅ 已接入（真机验证过）· ⭐ 传感器 ✅ 已接入（LHM 优先）·
> ⭐ 其余（LOGO 灯 / 功耗墙 / 键盘灯 / 风扇控制）⭐ **尚未接入** ⚠️

---

## 0. ⭐⭐ 一条铁律（⭐ 整个方案的基石）

```
⭐⭐ **能力位 = "已经接好下发路径"的证明** ⛔ 不是"硬件支持"的声明
   ⭐ 理由：⭐ UI 只认能力位 ⇒ ⭐ 一旦开出去，⭐ 用户点下去就会走到**已有的 GCU 下发代码** ⚠️
      ⇒ ⭐ 而宝龙达**没有 GCU**（⭐ 没有 MQTT 13688 服务 ✅）⇒ ⭐ 那条路必然失败/静默无效 ❌
   ⇒ ⭐ ⭐ **每开一个能力位，⭐ 必须先把它对应的下发路径分派到宝龙达后端** ✅
   ⭐ 反过来：⭐ **没接完之前，⭐ 能力位一律保持 false**（⭐ 沿用本树"⛔ 不假装可写"的约定 ✅）
   ⭐ ⭐ **这条铁律同时保证了"不影响同方"** —— 宝龙达的能力位只在 `ApplyBaolongdaBackendAsync`
      ⭐ 里赋值，⭐ 老同方走 `ApplyLegacyBackendAsync`（⭐ 一行都不改 ✅）、
      ⭐ GCU 机型走 `RefreshDeviceCapabilities`（⭐ 一行都不改 ✅）
```

## 2. ⭐ 逐个功能的实施要点

### 2.1 ⭐ LOGO 灯（⭐ 最简单、⭐ 建议先做）

```
⭐ 协议：⭐ 功能号 15（⭐ 读 `OutData[4]` = 0 关 / 1 开 ✅ · ⭐ 写 `InData[4]` = 0/1 ✅）
   ⭐ 真机已验证：⭐ 读到 `00 80 00 0F 01` ⇒ ⭐ **开** ✅
⭐ 代码：⭐ `BaolongdaWmi.TryReadLogoLight` / `TrySetLogoLight` ⭐ **已经写好了** ✅
⭐ 要做的：
   ⭐ ① ⭐ 在 `MechrevoHw` 加一个"宝龙达版"的 LOGO 灯读写入口（⭐ 仿 `SetLightingLevelAsync` 的形状）
   ⭐ ② ⭐ 找到 UI 切 LOGO 灯的入口（⭐ `Program.cs:2069` 「⭐ `logolight`」快捷开关 +
      ⭐ `HidLightbar_Logo/Ctrl` 那条灯效路径 ✅）⇒ ⭐ 在**宝龙达在管**时分派到 WMI ✅
   ⭐ ③ ⭐ `ApplyBaolongdaBackendAsync` 里 ⭐ 开 `LogoLight = true` ✅
⭐ ⚠️ 难点：⭐ LOGO 灯在我们的架构里**同时**属于"快捷开关"（⭐ 0/1）与"灯效"（⭐ 颜色/效果）两套 ⚠️
   ⭐ 宝龙达功能号 15 ⭐ **只有 0/1**（⭐ 没有颜色/效果 ❌）⇒ ⭐ 只能支持**开关**那一半 ✅
   ⇒ ⭐ 所以：⭐ 开 `LogoLight` 但 ⛔ **不开** `Lightbar` / `RgbLightbar`
      （⭐ 否则 UI 会显示颜色/效果选项 ⇒ ⭐ 点下去没反应 ❌）
```

### 2.2 ⭐ 功耗墙（⭐ PL1 / PL2 / 温度墙）

```
⭐ 协议：⭐ 功能号 23（⭐ `CpuPower` ✅）：
   ⭐ 写**单字节**：⭐ 0 = 关自定义 · ⭐ 1 = 开自定义 ✅
   ⭐ 写**两字节** `[子命令, 值]`：⭐ 2 = PL1(瓦) · ⭐ 3 = PL2(瓦) · ⭐ 4 = 温度墙(℃) ✅
   ⭐ 读：⭐ 只有 `OutData[4]` = "是否已开启"（⭐ **读不到 PL1/PL2/温度墙的当前值** ⚠️）
⭐ ⚠️⚠️ **这是最大的难点**：⭐ **只能写、读不回来** ⚠️
   ⭐ 而我们的 UI（⭐ `CustomModeForm` 的 `_pl1`/`_pl2` 滑块）⭐ 依赖 `hw.Pl1` / `hw.Pl1Minimum` /
      `Pl1Maximum` / `Pl1Adjustable` ⇒ ⭐ 这些**全来自 GCU 上报** ⚠️ ⇒ ⭐ 宝龙达**给不出来** ❌
   ⇒ ⭐ 两条路：
      ⭐ **路 A（⭐ 保守，⭐ 推荐先做）**：⭐ **只做"开关 + 三档预设"**，⛔ 不做连续滑块
         ⭐ 即：⭐ 让用户在"关 / 开(预设 PL1/PL2/温度墙)"之间选 ⇒ ⭐ 我们下发固定的一组值 ✅
         ⭐ 需要 ⭐ **宝龙达专属的 UI**（⭐ 见第 3 节 ✅）
      ⭐ **路 B（⭐ 完整）**：⭐ 自己**记住**用户设过的值（⭐ 本地设置持久化 ✅），
         ⭐ 界面上显示"上次下发的值"（⭐ 明确标注"本地记忆、⛔ 非从机器读回" ⚠️）
   ⭐ ⚠️ 且 ⭐ 真机验证时**要小心**：⭐ 写 PL1/PL2 会影响性能与发热 ⚠️
      ⇒ ⭐ 必须 ⭐ **先读回 `OutData[3]` 功能号回显做自校验** ✅，⭐ 且 ⭐ 初版**只允许保守的小范围值** ✅
```

### 2.3 ⭐ 键盘灯（⭐ 模式 / 颜色 / 亮度）

```
⭐ 协议：⭐ 16 = 模式（⭐ 0 关 / 2 RGB 固定色）· ⭐ 17 = 颜色（⭐ 写 3 字节 R,G,B）·
   ⭐ 18 = 亮度（⭐ 0~3 级）✅
   ⚠️ 真机**只验证过 15 / 8 / 13 / 22 / 20 / 23** —— ⭐ **16/17/18 没验证过** ⚠️
⭐ ⇒ ⭐ ⭐ **建议先用我们自己的程序在真机上试读一次**（⭐ 加个 `--baolongda-probe` 之类的开关），
   ⭐ 确认这三个功能号**调得通、⭐ 返回值合理**，⭐ 再动 UI ✅（⛔ 不要凭参考实现就开能力位 ⚠️）
⭐ ⚠️ 且 ⭐ 我们键盘灯那套是**很复杂的效果引擎**（⭐ 模式/颜色/方向/速度/分区 ✅）
```

## 3. ⭐ 「宝龙达专属 UI」怎么做（⭐ 且不影响同方）

```
⭐⭐ 三种做法，⭐ 按侵入性从小到大排：
   ⭐ **做法 1（⭐ 最安全，⭐ 推荐）**：⭐ **复用现有 UI，⭐ 只靠能力位控制可见性** ✅
      ⭐ 即：⭐ 宝龙达开哪些位 ⇒ ⭐ 界面上就只出现那几项 ⛔ 不出现的自然就藏了 ✅
      ⭐ 优点：⭐ **同方/GCU 的 UI 代码一行不动** ✅✅（⭐ 零回归风险 ✅）
      ⭐ 缺点：⭐ 有些地方"能力位粒度不够细"（⭐ 例如键盘灯：⭐ `Keyboard` 一开，
         ⭐ 整套效果引擎都出来了 ⚠️）⇒ ⭐ 那就得配合做法 2 ✅
   ⭐ **做法 2（⭐ 补充）**：⭐ 给 `MechrevoHw` 加一个"⭐ 宝龙达在管吗"的判据
      （⭐ 已有：⭐ `UsesBaolongda` ✅）⇒ ⭐ 在**少数几个**UI 判断点上加分支 ✅
      ⭐ 例：⭐ `if (hw.UsesBaolongda) { 只显示"开/关 + 颜色 + 亮度" } else { 原来的完整面板 }` ✅
      ⚠️ 规矩：⭐ **每个分支都必须以 `UsesBaolongda` 开头** ⇒ ⭐ 同方/GCU 走 else 原路 ✅
   ⭐ **做法 3（⛔ 不推荐）**：⭐ 单独做一套宝龙达专用的窗体
      ⭐ 缺点：⭐ 重复维护、⭐ 以后每加功能要改两处 ⚠️
   ⇒ ⭐ ⭐ **采用：⭐ 做法 1 为主 ＋ ⭐ 做法 2 补细节** ✅
```

## 7. ⭐⭐ 架构决策（2026-10-16 · 用户提出）：**前后端分离** —— 同一个按钮，不同机型下发不同指令

> ⭐ 用户原话：「⭐ 所以我在思考能不能前端和后端分离开，前端的同一个按钮在不同机型的指令可能是不一样的」

### 7.1 ⭐ 结论：⭐ **这套架构我们【已经有了】**，⭐ 只是还没贯彻到底 ✅

```
⭐ 已有的三件套（⭐ 这正是"前后端分离" ✅）：
   ⭐ ① ⭐ **后端枚举 + 有序候选表** ⇒ ⭐ `MechrevoBackendKind` ＋ ⭐ `MechrevoBackendOrder.Candidates`
      ⭐ 加一个新后端 = ⭐ **只加一项**，⛔ `MechrevoHw` 里不用改 else/if ✅
   ⭐ ② ⭐ **`MechrevoHw` 作为唯一门面** ⇒ ⭐ UI 拿到的永远是同一个对象 ✅
   ⭐ ③ ⭐ **能力位（`MechrevoDeviceCapabilities`）作为契约** ⇒ ⭐ UI 只问"这项有没有"，
      ⛔ 不问"这台机是什么后端" ✅
   ⇒ ⭐ ⭐ **"同一个按钮 → 不同指令"就是这么实现的** ✅
```

### 7.2 ⚠️ 但有一处**根本性的泄漏**：⭐ "命令"没有统一收口

```
⚠️ 现状：⭐ 有些操作**从 UI 直接发到 GCU 的 MQTT**，⭐ 绕过了后端抽象 ❌
   ⭐ 例：⭐ `Program.cs` 的 LOGO 灯 / ⭐ 灯效 ⇒ ⭐ 直接 `service.SetLightEffect(...)`
      ⇒ ⭐ 里面就是 `Publish("HidLightbar_Logo/Ctrl", …)` ⇒ ⭐ **硬绑 GCU** ❌
   ⭐ 而"性能档"那条**做对了**：⭐ UI → ⭐ `hw.SwitchLegacyModeAsync(...)` ⇒ ⭐ 内部**谁在管事调谁** ✅
⭐⭐ ⇒ ⭐ **这就是要改的东西**：⭐ 把"命令"从 UI/Service 挪进 `MechrevoHw`，
   ⭐ 用 ⭐ **意向命名**（⭐ `SetLogoLightAsync(bool on)` ✅）⭐ 而不是协议命名（⭐ `Publish("HidLightbar_Logo/Ctrl")` ❌）
```

### 7.3 ⭐ 目标形态（⭐ 三层各管各的）

```
⭐ **UI 层**（MechrevoLite）⭐ 只做两件事：
   ⭐ ① ⭐ 问能力位 ⇒ ⭐ 决定**显示不显示**这个控件 ✅
   ⭐ ② ⭐ 调**意向方法** ⇒ ⭐ `hw.SetLogoLightAsync(true)` ✅
   ⛔ **不再**关心 ⭐ 后端是谁 / ⭐ 发什么话题 / ⭐ 写哪个功能号 ✅
⭐ **门面层**（`MechrevoHw`）⭐ 负责**分派**：
   ⭐ `if (UsesBaolongda) → 写 WMI 功能号 15` ；⭐ `else → Publish GCU 话题` ✅
   ⭐ ⚠️ **所有后端差异都收敛在这一层**（⭐ 以及 `MechrevoService` 的少量分派 ✅）
⭐ **后端层**（`BaolongdaWmi` / GCU / `LegacyMifsWmi`）⭐ 只负责**协议细节** ✅
```

### 7.4 ⭐ 关于 `IsGcuConnected` 那 30 多处判断（⭐ 澄清：⭐ 大多**不是**泄漏）

```
⭐ 我数了一下：⭐ UI 层有 ⭐ **约 35 处** 判断 `IsGcuConnected` / `ActiveBackend` ⚠️
   ⭐ 但**绝大多数是正当的** ✅ —— ⭐ 它们干的是"⭐ **这项操作确实需要 GCU**（⭐ 发 MQTT）"，
      ⭐ 例如 `Program.cs` 里一堆"补发遥测/灯效恢复"⭐ ⇒ ⭐ 那些**本来就只能走 GCU** ✅
   ⭐ 真正算"泄漏"的只有 ⭐ **两类**：
      ⚠️ **类型一：⭐ 命令绕过后端**（⭐ 见 7.2 ⇒ ⭐ LOGO/灯效直发 MQTT ❌）⭐ **这是要改的** ✅
      ⚠️ **类型二：⭐ 展示文案按后端分支**（⭐ `SettingsForm.cs:6682` 的状态文字 ✅）
         ⭐ 影响很小 ⇒ ⭐ 可接受（⭐ 但更干净的做法是 ⭐ 后端自己给"状态文案" ✅）
   ⇒ ⭐ ⭐ **所以不要把 35 处都当成债务** —— ⭐ 真正要动的只有**类型一** ✅
```

### 7.5 ⭐ 落地做法（⭐ 与第 4 节的四步顺序**合并执行**）

```
⭐ 每接一个功能（⭐ LOGO 灯 / ⭐ 键盘灯 / ⭐ 功耗墙 / ⭐ 风扇 ⭐），⭐ 都按**同一个模板**：
   ⭐ ① ⭐ 在 `MechrevoHw` 加一个 ⭐ **意向方法**（⭐ 例：⭐ `SetLogoLightAsync(bool on)` ✅）
        ⭐ 内部 ⭐ `if (UsesBaolongda) → BaolongdaWmi.TrySetLogoLight(on)`
        ⭐ else ⭐ → ⭐ 原来那条 GCU 路径（⭐ **代码一字不改地搬进来** ✅）
   ⭐ ② ⭐ 把 UI 里**直发 MQTT** 的那一处 ⭐ 改成 ⭐ 调这个意向方法 ✅
   ⭐ ③ ⭐ 宝龙达能力位 ⭐ 开对应那一项 ✅
   ⭐ ④ ⭐ 验证：⭐ 同方/GCU 机型行为**逐位不变**（⭐ 只是命令换了个入口 ✅）＋ ⭐ 真机点一次 ✅
   ⇒ ⭐ ⭐ **做完这四步，⭐ "同一个按钮、不同机型不同指令"就自然成立了** ✅
   ⇒ ⭐ 而且 ⭐ **每一步都顺手把"类型一泄漏"清掉一处** ✅（⭐ 不是先做大重构 ⚠️）
```

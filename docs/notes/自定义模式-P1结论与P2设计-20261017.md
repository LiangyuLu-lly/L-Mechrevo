# 自定义模式开放 + 多配置：P1 结论与 P2 设计（2026-10-17）

> 用户口径：「把自定义模式开放吧」；「LM 我记得有自己的配置存储位置，可否把宝龙达模具也做成多配置而不是隐藏」
> 「以后如果解耦 GCU，GCU 的配置保存肯定不能一直用」⇒ 目标：**配置归 LM，GCU 只当执行器之一**。
> 本轮先做 **P1（存储）**，P2（路由）紧随。

---

## 一、P1 结论：**存储已经存在，不需要新建**

| 部件 | 现状 | 位置 |
|---|---|---|
| 每档参数 | `PerfModeSettings`（PL1/PL2/PL4/GpuTgp/风扇 duty/Tcc/GPU 超频/显存偏移/FanBoost/刷新率/电源计划…） | `source\MechrevoLite.Mode\PerfModeSettings.cs` |
| 落盘 | AppConfig 键 `mode_tune_<modeId>_*`（在 `%APPDATA%\MechrevoLite\config.json`） | `PerfModeStore`（`SaveSettings` / `LoadSettings`） |
| 多自定义档 | ✅ 已有 `custom1..custom5`（`custom_last_profile`、`PerfModeDefinition.CustomId(n)`） | `PerfModeStore` 迁移段 |
| 模式↔固件槽绑定 | `ModeProfileConfig`（视觉模式 → 固件槽索引/名字） | `source\MechrevoLite.Mode\ModeProfileConfig.cs` |

⇒ ⭐ **"LM 自己的配置存储"确实存在**；真正依赖 GCU 的只有两处：
1. **路由**：自定义档固定 `PerfModeRoute.FirmwareSlot`，而 `PerfModeCapabilities.SupportsFirmwareSlot = !hw.UsesBaolongda`
   ⇒ 宝龙达上 `canWriteFirmwareSlot=false` ⇒ 计划为空（日志 `custom1 -> (no steps)`）⇒ 界面提示"本机无 GCU"。
2. **槽位绑定**：`ModeProfileConfig` 的槽数来自 `PerfModeService.SlotCount`（GCU 才有）。

⇒ P1 **无需写代码**；需要补的只有"风扇曲线/亮度"是否要按档保存（P2 里先用**全局**那份，不按档，避免与
`BaolongdaFanCurveStore` 出现两份事实）。

## 二、P2 设计：`PerfModeRoute.Local`

### 2.1 新增路由

```csharp
public enum PerfModeRoute { BuiltIn, FirmwareSlot, Local }
```

- `Local` 语义：**不碰固件槽**，按 `PerfModeSettings` 逐项下发到**本机后端**，然后按回读结果判定成功。
- 判定：`PerfModeBackend.SupportsFirmwareSlot` 为 false（宝龙达）时，自定义档的 `Route` 从 `FirmwareSlot` 改判为 `Local`。

### 2.2 步骤（复用已有本地路径，⛔ 不新写协议）

| 顺序 | 步骤 | 现有入口 | 确认方式 |
|---|---|---|---|
| 1 | PL1 / PL2 / 温度墙 | `MechrevoHw.TryApplyCpuPowerLimitViaBackend`（功能号 23） | 写入成功（协议读不回，如实标注） |
| 2 | 风扇曲线启用/停用 | `SaveBaolongdaFanCurve`（20/21 软件闭环） | 既有 `confirmed` |
| 3 | GPU 核心/显存偏移 | 现有 `NvidiaGpuControl`/NVAPI 路径 | 既有回读 |
| 4 | 亮度 | 现有亮度下发 | 既有 |

⚠️ 顺序原则：**先散热（PL/风扇）再性能（GPU 偏移）**，与 `PerfModeApplyPlanner` 现有顺序一致。

### 2.3 失败与回滚

- 任一步失败 ⇒ **不中断**（与 GCU 那条一致），收集到 `PerfApplyOutcome`，UI 如实显示"哪几步没确认"。
- 切到**别的档**时：`Local` 档的 PL/风扇属于"覆盖项"，切走时必须按新档的 `PerfModeSettings` 重写
  （⛔ 不能让上一档的 PL 留在机器上）—— 这正是现在 GCU 的 `FirmwareSignature` 已经在做的事，`Local` 沿用同一判据。

### 2.4 UI

- 自定义按钮可见性：现在 `flagCustomMode = flag17 && !SupportsModeProfileConfig`（30 系/模式×配置机型隐藏）。
  P2 改为 **「有可用路由」**：`flag17 && (SupportsFirmwareSlot || 本地参数下发可用)` ⇒ 宝龙达显示并可用。
- 自定义档内的"固件档 N"字样：宝龙达下替换为「本机配置」（已有 `FirmwareSlotUnsupportedText` 的语义）。
- 30 系仍需保持隐藏（官方无自定义档、无法回读），判据不变。

### 2.5 迁移（为将来彻底解耦）

1. `ModeProfileConfig` 的绑定改为**可选**：无 GCU 时不绑定槽位，只记 LM 档案 id；
2. 有 GCU 时保留"同时写固件槽"兼容行为；
3. 未来去掉 GCU：把 `FirmwareSlot` 路由整体标为 deprecated，`Local` 成为唯一实现 —— 此时配置与执行彻底分离。

## 三、验证口径

- **本机（同方 GCU）**：能验"没回归"——自定义档仍走 `FirmwareSlot`，步骤与改前逐位一致（自检 + 日志比对）；
- **40 系真机**：自定义按钮可见 → 改 PL/温度墙 → 应用 → 日志出现 `route=Local` 与逐项结果；
  切走档位后 PL 被新档覆盖；重启后配置仍在（`mode_tune_*`）。
- 不能在本机验：宝龙达的 `Local` 真正生效（必须真机）。

## 五、P2 第一批落地（2026-10-17 · 机主指出"滑块是灰的"）

**根因**：`CustomModeForm.SetOptionsEnabled` 里那条锁：

```csharp
bool locked = hw != null && IsGen40Plus(hw) && (mode == null || !mode.IsCustom) && !_firmwareMode;
```

原意是"Gen40+ 的预设档由**固件（GCU）**持有，改 LM 的值不生效还会被顶回去"。
但宝龙达**没有 GCU** ⇒ 这个理由不成立；而它的 PL/温度墙**能走 WMI 23 真下发**
（`PerfModeCapabilities.SupportsWmiPowerFields = UsesBaolongda`）⇒ 不该再锁。

**改法**：`locked` 追加 `hw.IsGcuConnected` 判据 ⇒ 无 GCU（宝龙达）时选项可编辑；
GCU 机型（含 Gen40+）判据**逐位不变**。

**下一步（未做）**：
- 自定义档的 `EnsureFirmwareSlotAsync` / `SwitchFirmwareSlot` 在 `SupportsFirmwareSlot=false` 时跳过，
  以"本地字段全部确认"作为切档成功；
- 自定义按钮/磁贴的可用性判据改成"有可用路由"。

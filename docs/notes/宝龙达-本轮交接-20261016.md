## 三、本轮的重大发现（改变了方向，必读）

### 1. 限充其实能做 —— 我们之前判断错了

之前结论「宝龙达/蛟龙不支持限充」有两条硬证据，现在看都是**通道选错**导致的：

- 我们走 `\\.\ACPIDriver` + H2RAM，偏移 `0x07B9`（上限）/`0x07D0`（复充下限）/`0x7C3`（门控），
  这套来自上游 `Leo-stro/mechrevo-charge-limit`
- **真正的充电控制在 EC 端口 I/O + XRAM**：端口 `0x66`（命令 `0x92` 读 / `0x93` 写）＋ `0x62`（数据），
  XRAM 地址 `0x8150`（mailbox 主命令，写 `0x10` 触发）/ `0x8151`（子命令）/ `0x8152`（结果 `0x55` 成功）/
  `0x8153`（阈值上限）/ `0x8154`（阈值下限）/ `0x83C0`（模式）/ `0x847C`（SOC）/ `0x8410-0x8413`（EC 版本）
- 子命令：`0x0D` 启用原生阈值 / `0x0E` 停充 / `0x0F` 恢复；模式值 `0x00` 正常 / `0x02` 停充 / `0x48` 原生阈值
- 开源项目 `Zcodeoooo/JiaoLong16Pro-Battery-threshold` 在**相同硬件**（宝龙达代工、MRID6/BM5235、ITE IT5570、
  EC `00.28.00.00`）实测成功：SOC 61% 时充电速率 17230 → 0，上限 80／下限 60 正确回读，
  `native_enabled: true, ec_autonomous: true, resident_program_required: false`（**EC 自主接管、不需常驻进程**）

⇒ 用户已决定**限充暂缓**。但方向已经清楚：要走端口 I/O，且需要给 PawnIO 自建 EC 模块。

### 2. IOCTL 返回成功 ≠ 地址可达（这条最重要）

`UWACPIDriver` 对**窗口外的地址不报错，而是回 `0xFF` 填充值**。本机实测：

```
对照读（H2RAM 已知可读 · 0x7C3）= 可读，值 = 0x07     ← 真实值
试读 XRAM 0x8410~0x8413 = 可读，原始字节 = 0xFF ×4
```

⇒ **判据必须是「值本身合理」，不能是「调用没报错」。**

这条回溯解释了 `01086f4` 修的那个 bug：老的「固件预检」在 `0x770`/`0x87F` 读到 `0xFF` 就判"本机固件不支持限充"，
其实是在看填充值。`EcChargeLimit.cs` 里那段注释当年就怀疑过"`0xFF` 更可能是未映射填充值"，现在有了机制层面的确认。

**以后凡是碰 EC 的读写，都要先做一次"已知可读地址"的对照读**，否则分不清"通道不通"和"地址不可达"。

### 3. 合规红线（写代码前必须知道）

- `WinRing0x64.sys`：签名者 CrystalMark，**签名有效期 2007/2/5–2014/1/27 已过期**，且在微软 Vulnerable Driver Blocklist 里。
  蛟龙那个项目的 README 直接要求用户"取消易受攻击驱动阻止列表""关闭内存完整性"⇒ **绝不能随包分发**
- `inpoutx64.dll`：官方许可只自由用于个人/非商业 ⇒ 随包分发有风险
- **正路**：我们已有的 PawnIO（`PawnIOWrapper.cs` 暴露 `Connect`/`LoadModule`/`Execute`，模块制，
  目前只带 `RyzenSMU.bin`/`IntelMSR.bin`）——它是 WinRing0 的现代安全替代品，同样支持端口 I/O。
  需要评估：给它写一个 EC 端口 I/O 模块要多少工作量、端口原语够不够用
- 意外收获：`UWACPIDriver` 本身是 **WHQL 签名**（`CN=Microsoft Windows Hardware Compatibility Publisher`，签名有效），
  是三者中唯一能合法随包分发的

### 4. 许可纠错

`DOUZHANZHE-Control`（斗战者）**不是 MIT，是 GPL-3.0**（`README.md:153-155`）。GPL 有传染性，只能取协议事实，不能碰代码。
`BellatorFanControl` 许可不明（只有 README 无 LICENSE）。蛟龙限充项目**仓库里没有 LICENSE**，还把 `WinRing0x64.sys` 二进制直接放进仓库。

⇒ **三个项目都只能取"事实"（地址、命令字、偏移表、做法），绝不照抄代码。**

### 5. `FirmwareSlot` 是错的模型

我们原来把自定义档映射成 `PerfModeRoute.FirmwareSlot`，并让风扇曲线依赖它。**这是错的。**
正确关系：

- 「档位」（静音/平衡/狂暴/自定义）→ 后端模式切换（功能号 8 / 23）
- 「风扇曲线」→ **独立软件引擎**（定时器轮询温度写转速，走功能号 20/21）
- **两者正交：切档不换曲线**

依据：蛟龙和斗战者的风扇曲线都是"应用自己的配置 + 软件轮询"，与固件槽无关。
`f1c226f` 已经把 `BaolongdaFanCurveStore` 的 `FirmwareSlot` 依赖拆掉；`PerfModeService` 那边按方案 §5 属独立排期，**还没动**。

### 6. 斗战者也用端口 `0x62/0x66` 直写 EC

它的 `README.md` 写着 `EC 直写 | inpoutx64 (IO 端口 0x62/0x66)`，和蛟龙限充项目**同一个通道**。
两个宝龙达代工的项目独立地都用了它 ⇒ 这条路在宝龙达硬件上是通的。

它还留了一条经验：**端口直写某些寄存器会被固件在 30ms 内覆写回原值** ⇒ 写完必须回读，不能假设成功。

它的 EC 物理内存窗口（DSDT 的 `OperationRegion (ECF2, SystemMemory, 0xFE800400, 0xFF)`）偏移表：
`0x9A` 键盘背光 / `0x20` Fn 锁 / `0x25` Caps·Num / `0xE4` 散热模式 / `0xE0` GPU 温度 / `0xE1` CPU 温度 /
`0x96`·`0x97` GPU 风扇转速 / `0x9B`·`0x9C` CPU 风扇转速 —— **里面没有任何电池项**，所以这条路对限充没用。

### 7. `UWACPIDriver` 被双重挡在 GCU 分支下（安装包疏漏）

`installer-src\install_script.iss:160-163` 那三条 `Source` 同时受 `#ifndef NOGCU`（编译期）和
`Check: ShouldInstallGcu`（运行期）限制。机主装的是 `/DNOGCU` 包，第一道就把文件排除了；即使进包，第二道也会拦住
（`ShouldInstallGcu()` 在宝龙达机型返回 false）。执行安装的 `[Run]`（调 `Install-Gcu.ps1`）也带同一个 Check。

而 `:119-124` 的注释说 2026-10-13 用户要求把它"变成标准自带"、"不再依赖 GCU 载荷是否落盘"——
当时只把它从 `payload\GCU\` 挪到 `shared\`，**没从这两个条件下面摘出来**。对宝龙达机型那句"标准自带"从未成立。

⚠️ 但**即使装上也没用**：它的 H2RAM 窗口是 `0x700–0x7FF`（256 字节），而 XRAM 的 `0x8150` 远超窗口，
机制上到不了 XRAM。所以"自家驱动 + 蛟龙那套 XRAM 地址表"这个组合**不成立**。

## 六、陷阱清单（本会话反复踩过，务必遵守）

1. **`Strings*.resx` 是混合行尾**（`zh-CN`：CRLF=14 / 裸 LF=5343）⇒ ⛔ **绝不要用 `edit` 工具**。
   要么用脚本做字节级子串替换并回验行尾计数，要么把文案放在代码里（已有先例）
2. **各文件行尾不同**：`SettingsForm.cs`/`MechrevoHw.cs`/`MechrevoService.cs`/`HardwareControl.cs` 纯 LF；
   `EcChargeLimit.cs`/`LightForm.cs` 是 CRLF；`Strings*.resx` 混合。**改前先看 HEAD，改后回验**
3. ⛔ **别用 PowerShell `>` 读原版做比对**（会把 LF 转成 CRLF，导致误判"原版是 CRLF"）
4. **`Logger.WriteLine` 的级别由消息内容判定** ⇒ 不保证在默认「仅错误」级别下落盘。
   关键诊断必须用 `Logger.WriteError`；周期性日志按状态翻转只记一次（`TryMarkChanged`）
5. **`Logger` 的真实重载里没有 `errorLevel:` 具名参数**（有人踩过 CS1739）
6. **`MechrevoLite.dll` 里搜不到字符串** ⇒ 别拿"dll 串检查"当证据
7. **看到编译错误先核对"报错行号与磁盘内容是否一致"** ⇒ 不一致就是撞上了别人正在写的中间态，重编即可，别去改那些行
8. **`Get-CimInstance` 查 `AcpiTest_*` 这类类会得到 0 个实例的假否定** ⇒ 这类要用 `ManagementObjectSearcher`
9. **多路并行时只 `git add` 自己的文件**。本会话多次发生"部署的 dll 里含别人未提交的改动"，
   出异常时先排除别人那部分
10. **本机是 GCU 机型（同方翼龙15Pro / `GM5HG0A`）**，宝龙达分支走不到 ⇒
    宝龙达侧改动**只能靠代码路径证明 + 本机"正确 decline"实证**，必须明确说清哪部分需真机验

## 七、铁律

- **非宝龙达机型 / 非 GCU 机型逐位不变**（所有改动的第一约束）
- ⭐ **仓库外面有用的材料，一律移进仓库** —— 落点 `D:\openLM\_upstream\`（`.gitignore:67` 已忽略，
  大二进制不进 git）。原因：`%TEMP%` 会被系统清、`Downloads` 会被清、回收站甚至会被误清。
  这是活教训 —— 那 65.9 MB 限充材料一度**只存在于** `%TEMP%\jl-bt`，
  而 `Downloads` 里三个原始包曾**被删光**、靠回收站才找回。归档规矩与台账见
  [`参考材料-来源与本地位置.md`](参考材料-来源与本地位置.md)
- ⭐ **先判模具归属（同方 / 宝龙达），再决定参考什么** —— 同方的实现不能当宝龙达的参考，反之亦然。
  **已经栽过两次**：①限充——拿同方 H2RAM `0x07xx` 去蛟龙上找充电寄存器，读回 `0xFF` 就判"不支持"，
  其实该看宝龙达的 XRAM `0x81xx`；②校色——曾以为同方那两个 `ControlCenter` 包里藏着厂商实现，
  实际那是同方模具、对宝龙达无参考价值。⚠️ 而"**宝龙达没有校色**"这条依据来自 **`JiaoLong7.3`（第三方修改版）**、
  **不是原厂结论** —— 原厂宝龙达控制台我们手上没有（材料缺口）。第三方修改通常只增不减 ⇒ 原厂大概也没有，
  但**这一点带不确定性**。实用上仍只能靠 Windows 标准 API。
  **搞错模具，整个调研方向就跑偏。**
- ⭐ **参考优先级（用户定的）**：**协议事实**（地址/命令字/寄存器/时序）优先信**蛟龙第三方**（机型一致度最高）；
  **工程做法**（防抖回差、启动清理、退出恢复、睡眠恢复、Tick 防重入、偏离检测＋分级恢复、原子写配置、

## 十一、充电阈值基线静态挖掘 + 控制台 EC 通道（提交 `d7a6ea3`）

### 1. 出厂默认阈值**不存在** —— 这是本轮最重要的结论

在 `ec_35.bin` 里搜"给阈值寄存器写立即数"的 8051 模式（`90 81 53 74 XX F0`）：
写进 `0x8153` 的全是 `1` / `2` / `0xEE` 这类**控制标志**，没有任何 50/60/80 的初值；
`0x8154` 连"立即数直写"模式都找不到。

⇒ **阈值完全由 Host 下发，固件不预设。**

**真正的基线是「模式 0 = 不做阈值控制 = 充到 100%」**，静态即可确定：
`native_enable.jsonl` 的 `phase=before` 与 `native_disable.jsonl` 的 `phase=complete` 都是 `83C0=00`；
原生生效中才是 `48`。而 `83A1/83A2` 在模式 0 下不生效（恢复原厂后仍是 `50/3C`，那只是残值）。

**⇒ 充电阈值那条，机主不必先用官方控制台记基线。**（验证计划里的这一步可以删掉）
**⇒ 回滚不是"写回某个原值"，而是发恢复命令 `0x0F` 让模式回 0** —— 这也解释了那个项目
为什么能在"读不回原值"的前提下安全实验。

⚠️ **这条只适用于充电阈值。功耗墙/温度墙是另一套**（功能号 23 只写不读，确实拿不到当前值），
那边"先用官方控制台记基线"的建议**仍然成立**。

被排除掉的"像基线但其实是别人设计值"的东西：`bm5235_battery.py:56` 的 `hysteresis(low=60, high=80)`、
`bm5235_native.py:162` 的 `enable_native(low=60, high=80)`、`--low/--high` 的 argparse 默认值、
`Windows\Control60_80.cmd`（文件自述 "Continuous 60/80 experiment"）、
`battery-hardware-limit.zip`（OpenRevo 插件，插件设计值）、

### 2. XRAM 地址表：三重独立确认

| 确认方式 | 结果 |
|---|---|
| **EC 固件硬编码** | 搜 `MOV DPTR,#addr`（`90 hi lo`）：`0x8153` 被引用 **42 次**、`0x8154` 11 次、`0x83C0` 15 次、`0x847C` 12 次……与开源项目地址表**逐项吻合** |
| **固件控制链** | `@0x04693: 90 81 53 \| E0 90 83 A1 F0`（读 `0x8153`→写 `0x83A1` 复制上限）；<br>`@0x0469B` 同理复制下限到 `0x83A2`；`@0x0442A`/`@0x03E50` 再与 SOC `0x847C` 比较（SUBB / CLR C）决定停充/恢复 |
| **ACPI 层反证** | 全部 `dsdt.dsl` ＋ `ssdt0-16.dsl` 搜 `0x8150`~`0x8154`/`0x83C0`/`0x847C`/`0x8370`/`0x83A0`~`0x83A2` ⇒ **零命中** |

第三条最关键：**XRAM 是 EC 固件内部地址空间，只能经端口协议访问，不经过 ACPI OperationRegion**
⇒ 从机制上解释了我们的 `\\.\ACPIDriver`（H2RAM `0x700–0x7FF`）**永远到不了 XRAM**。

`ec_35.bin` 与 `ec_40.bin` 131,073 字节里**只差 15 字节**，引用完全一致 ⇒ **布局跨 BIOS 35/40 稳定**。

（顺带：`dsdt.dsl:5214` 确有 `OperationRegion (ECF2, SystemMemory, 0xFE800400, 0xFF)`，
与斗战者注释一致，但只有 `0xFF` 字节，到不了 XRAM。）

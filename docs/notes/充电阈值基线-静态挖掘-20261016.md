# 充电阈值「出厂基线」静态挖掘结论（2026-10-16）

任务：不靠机主、不碰硬件，从静态材料里挖宝龙达/蛟龙的充电阈值默认基线。
结论先说：**「出厂默认阈值数值」不存在，也不需要 —— 真正的基线是「模式 0 = 不做阈值控制」，这个可以从静态材料完全确定。**

---

## 一、默认基线的最终答案

### 基线不是一个数值，而是一个状态

`JiaoLong16Pro-Battery-threshold` 的实测记录给出了直接证据：

| 记录 | 文件 | `83C0` 模式 | `83A0` 子状态 | `8370` 状态 | `83A1/83A2` |
|---|---|---|---|---|---|
| 启用原生**之前** | `native_enable.jsonl` 第 1 行 `phase=before` | `00` | `00` | `04` | `50/3C` |
| 恢复原厂**之后** | `native_disable.jsonl` `phase=complete` | `00` | `00` | `04` | `50/3C` |
| 原生**生效中** | 两份记录的中间行 | `48` | `01`→`02`/`03` | `32` | `50/3C` |

两个关键事实：

1. **`83C0=00`（模式 0）就是出厂状态** —— 启用前和恢复后都是 `00`，而原生阈值模式是 `48`。
2. **`83A1`/`83A2` 在模式 0 下【不生效】** —— 恢复原厂后它们仍是 `50/3C`（=80/60），因为那只是上次写入的**残值**，模式 0 下固件不读它们。

⇒ **出厂基线 = 模式 0 = 不做任何阈值控制 = 正常充到 100%。**
不存在"出厂时上限是 X、下限是 Y"这回事。

### 阈值完全由 Host 下发，固件不预设

在 `ec_35.bin` 里搜"给阈值寄存器写立即数"的 8051 模式（`90 81 53 74 XX F0`）：

```
0x8153: @0x04811  MOV A,#0x01  → 0x8153
        @0x04818  MOV A,#0x02  → 0x8153
        @0x0481F  MOV A,#0xEE  → 0x8153     ← 238，控制标志
        @0x04AA6  MOV A,#0x01  → 0x8153
0x8154: 未找到任何"立即数直写"模式
```

写进去的全是 **1 / 2 / 0xEE 这类控制标志**，**没有任何 50/60/80 的阈值初值**。
⇒ 固件不预设阈值，完全等 Host 下发。这也解释了为什么 `NATIVE_README.md` 里的 60/80 是**作者自己选的实验值**（脚本参数默认 + `Control60_80.cmd` 的命名），不是出厂值。

### 其他"像基线"的来源，逐个排除

| 来源 | 是不是出厂基线 | 依据 |
|---|---|---|
| `bm5235_battery.py:56` `hysteresis(soc, stopped, low=60, high=80)` | ❌ 脚本参数默认 | 函数签名默认值 |
| `bm5235_native.py:162` `enable_native(ec, low=60, high=80, ...)` | ❌ 同上 | 同上 |
| `--low/--high` argparse `default=60/80` | ❌ 同上 | `:354-355` |
| `Windows\Control60_80.cmd` | ❌ 作者实验脚本 | 文件内容自述"Continuous 60/80 experiment" |
| `battery-hardware-limit.zip`（OpenRevo 插件） | ❌ 插件设计值 | `manifest.json` 描述"真实生效 60%/80% 硬件限电"，`target_slot=power.hardware_limit` |
| `GamingControlCenter.Properties.Settings` | ❌ 空 | 只有一个 `Default` 属性，没有 `DefaultSettingValue` |
| `Models.CPUPower` / `CPUTempWall` | ❌ 只有 Set/Get | 无默认值常量（见第四节） |

### 对验证计划的影响

**机主可以不必先用官方控制台记基线。**

原因：
- 基线是「模式 0 / 不限制」，静态即可确定，不需要读某台机器
- 我们做任何阈值配置前，本来就应该先确保 EC 处于模式 0（那个项目的 `NativeEnable.cmd` 就是这么做的：
  "若旧程序留下已核对的停充模式 `02`，原生启用程序会先调用 `0x0F` 恢复并等待固件清理状态"）
- **回滚不是"写回某个原值"，而是发恢复命令让模式回 0**（`0x0F`）——
  这也解释了为什么那个项目能在"读不回原值"的前提下安全实验

⇒ **原先"让机主用官方控制台记 PL1/PL2/温度墙基线"那一步，对充电阈值不必要**。
（对功耗墙/温度墙仍然必要 —— 见第五节，那是另一套东西。）

## 二、XRAM 地址映射的独立确认（三重）

### 第一重：EC 固件里硬编码（最强证据）

在 `ec_35.bin` 里搜 `MOV DPTR,#addr`（字节 `90 hi lo`）：

| XRAM 地址 | ec_35 出现次数 | ec_40 出现次数 | 首次偏移 |
|---|---|---|---|
| `0x8150` | 3 | 3 | `0x4AF6` |
| `0x8151` | 7 | 7 | `0x4546` |
| `0x8152` | 4 | 4 | `0x4540` |
| **`0x8153`** | **42** | **42** | `0x459A` |
| `0x8154` | 11 | 11 | `0x469B` |
| `0x83C0` | 15 | 15 | `0x268D` |
| `0x83A0` | 5 | 5 | `0x3E10` |
| `0x83A1` | 2 | 2 | `0x442A` |
| `0x847C` | 12 | 12 | `0x31E4` |

⇒ 这些地址在固件里是**绝对地址绑定**的，与那个开源项目的地址表**逐一吻合**。
⇒ `ec_35.bin` 与 `ec_40.bin` **131,073 字节里只差 15 字节**，上述引用完全一致
⇒ **XRAM 布局跨 BIOS 35/40 稳定**（印证原理分析里"厂商用绝对地址把 mailbox 固定下来"的说法）

### 第二重：控制链在固件里可读出来

```
@0x04693:  90 81 53 | E0 90 83 A1 F0       读 0x8153 → 写 0x83A1   （复制上限）
@0x0469B:  90 81 54 | E0 90 83 A2 F0 22    读 0x8154 → 写 0x83A2   （复制下限）
@0x0442A:  90 83 A1 | E0 FF 90 84 7C E0 9F  读 0x83A1 → 读 0x847C(SOC) → SUBB  （上限比较）
@0x03E50:  90 83 A2 | E0 FF 90 84 7C E0 C3  读 0x83A2 → 读 SOC → CLR C      （下限比较）
```

⇒ **完整证实**：Host 写 `0x8153`/`0x8154` → 固件复制到 `0x83A1`/`0x83A2` → 固件用它们与 `0x847C`(SOC) 比较决定停充/恢复。
⇒ 与 `NATIVE_README.md` 的表格（"复制后的上限 `83A1=50`、下限 `83A2=3C`"）完全一致。

### 第三重：ACPI 层**没有**这些地址（反证必须走端口 I/O）

全部 `dsdt.dsl` + `ssdt0-16.dsl` 里搜 `0x8150`~`0x8154` / `0x83C0` / `0x847C` / `0x8370` / `0x83A0`~`0x83A2`：
**零命中**。

⇒ XRAM 地址在 ACPI 层完全没有声明 ⇒ 它们是**EC 固件内部地址空间**，
只能经端口协议访问（`0x62/0x66` + `0x92/0x93`，或官方的 `0x2E/0x2F`），
**不经过 ACPI OperationRegion**。
⇒ 这从机制上解释了为什么我们的 `\\.\ACPIDriver`（H2RAM 内存映射窗口 `0x700–0x7FF`）永远到不了 XRAM。

顺带确认：`dsdt.dsl:5214` 有 `OperationRegion (ECF2, SystemMemory, 0xFE800400, 0xFF)` ——
与斗战者注释里的声明**完全一致**，证明蛟龙 DSDT 里确实有那个物理内存窗口，但它只有 `0xFF` 字节，**到不了 XRAM**。

## 三、XRAM 阈值寄存器的可读性：**可读**

- 那个项目实测："**上限 80、下限 60 已正确回读**"（`NATIVE_README.md`）
- 代码里有读回校验：`bm5235_native.py:188`
  `if ec.read(0x8153) != high or ec.read(0x8154) != low: raise ...`
- 读协议：向 `0x66` 发 `0x92`（读）/ `0x93`（写）→ 经 `0x62` 依次传地址高字节、地址低字节、数据

⇒ **XRAM 的 `0x8153`/`0x8154` 可读可写**，但**前提是具备端口 I/O 能力**。

⚠️ 注意与我们的现状对比：
- 我们的**功能号 23 只写不读** ⇒ 拿不到功耗墙/温度墙的当前值（见第五节）
- 但**充电阈值走 XRAM，是可读的** ⇒ 一旦有端口 I/O，读基线完全可行

## 四、额外重大收获：官方控制台 7.3 的 EC 通道

`D:\Downloads\JiaoLong7.3.rar`（JiaoLong Control 7.3，88.3 MB，576 条目）
主业务程序集：`第三方蛟龙游戏控制中心.dll`（23,299,584 B），另有 `.pdb`（115,896 B）与 `.deps.json`。

### 官方只用 88 个类型，且**没有充电阈值功能**

全部类型里与电源相关的只有：
`Models.CPUPower` · `Models.CPUTempWall` · `Models.Fan` · `Models.GpuMode` · `Models.Keyboard` ·
`Models.LogoLight` · `Models.PerformaceMode` · `EC.RW.ECRW_Tool`

⇒ **没有任何 `Battery` / `Charge` / `Threshold` 类** ⇒ 官方控制台 7.3 确实**不做充电阈值**
（与用户此前的说法一致，现在有反编译级证据）。

而 `EC.RW.ECRW_Tool` **只有风扇方法**：

```csharp
public static void Fan_Init()  { SMUCommands.RyzenAccess.Write_EC_Init(); }
public static void Fan_Speed(byte speed) {
    SMUCommands.RyzenAccess.Write_EC_EX(51260, speed);   // 0xC83C
    SMUCommands.RyzenAccess.Write_EC_EX(51261, speed);   // 0xC83D
    byte b = SMUCommands.RyzenAccess.Read_EC_EX(2848);   // 0xB20
    b |= 2;
    SMUCommands.RyzenAccess.Write_EC_EX(2848, b);
}
public static void Fan_Clear() { ... 三个地址清零 ... }
```

⚠️ `51260/51261` = **`0xC83C`/`0xC83D`**、`2848` = **`0xB20`** ——
与蛟龙开源项目（`JiaolongControl`）用的 EC 地址**完全吻合**（"写 `0xC83C`/`0xC83D`，`0xB20` 置 bit1/bit3"）。

### 官方怎么读写 EC：WinRing0 + 端口 `0x2E/0x2F`

```csharp
// RyzenSmu.Smu
using OpenLibSys;                                  // WinRing0 的 OpenLibSys
private Ols RyzenNbAccesss = new Ols();
RyzenNbAccesss.InitializeOls();                    // 抛 "WinRing OLS_DRIVER_NOT_LOADED" 等

public bool Write_EC_EX(ushort iIndex, byte data) {   // iIndex = 16 位 XRAM 地址
    if (ECStatus(EC_IBF)) {
        RyzenNbAccesss.WriteIoPortByte(EC_ADDR_PORT, 46);   // 0x2E
        RyzenNbAccesss.WriteIoPortByte(EC_DATA_PORT, 17);   // 0x11
        RyzenNbAccesss.WriteIoPortByte(EC_ADDR_PORT, 47);   // 0x2F
        ...
    }
}
public byte Read_EC_EX(ushort iIndex) { ... 同样 0x2E/0x2F ... }

public void Write_EC_Init() {                      // 访问前的芯片识别/解锁
    EC_CHIP_ID1 = Read_EC_EX(8192);                // 0x2000
    EC_CHIP_ID2 = Read_EC_EX(8193);                // 0x2001
    if (85 == EC_CHIP_ID1) {                       // 0x55
        EC_CHIP_Ver = Read_EC_EX(4192);            // 0x1060
        EC_CHIP_Ver |= 128;                        // 置 bit7
        Write_EC_EX(4192, EC_CHIP_Ver);
    }
}
```

关键点：
1. **官方用 WinRing0（`OpenLibSys.Ols`）做端口 I/O**，端口是 **`0x2E`（地址/索引）/ `0x2F`（数据）+ 命令 `0x11`**
   —— 与开源项目的 `0x62/0x66` + `0x92/0x93` 是**两套不同的端口协议**，但都能访问同一片 XRAM
2. **`iIndex` 是 `ushort`（16 位）** ⇒ 这条通道**能访问任意 XRAM 地址**，包括 `0x81xx`
3. **`Write_EC_Init()` 是访问前的必要前置**：读 `0x2000`/`0x2001` 芯片 ID（期望 `0x55`），
   再把 `0x1060` 置 bit7 解锁 —— **这是一个我们此前完全不知道的解锁步骤**
4. ⚠️ **官方控制台自己也分发 `WinRing0x64.dll`**（就在 `JiaoLong7.3\` 目录里）

⇒ 这条通道技术上完全能读 `0x8153`/`0x8154`，但**官方没有用它做充电阈值**。

### 合规含义

- 官方控制台自己随包分发 WinRing0 ⇒ 说明厂商认为这样分发是可接受的
- 但 WinRing0 仍在微软 Vulnerable Driver Blocklist 里、签名早已过期（CrystalMark，2007–2014），
  第三方项目 README 还要求用户"取消阻止列表 / 关闭内存完整性"
- **我们自己的 PawnIO 是更干净的替代**，且 `Write_EC_Init` 这套前置流程说明
  "访问 XRAM 前需要解锁" —— 这是设计 PawnIO EC 模块时必须包含的一步

## 五、附带收获：官方功耗墙/温度墙的实现（直接印证我们的做法）

```csharp
// Models.CPUPower
public static void SetCpuShortPower(byte LongPower)  { WMIMethodServices.SetValue(WMIMethodName.CPUPower, new byte[2]{ 2, LongPower }); }
public static void SetCpuLongPower (byte ShortPower) { WMIMethodServices.SetValue(WMIMethodName.CPUPower, new byte[2]{ 3, ShortPower }); }

// Models.CPUTempWall
public static void SetCPUTempWall(byte v) { WMIMethodServices.SetValue(WMIMethodName.CPUPower, new byte[2]{ 4, v }); }
public static float GetCPUTempWall()      { return WMIMethodServices.GetValue<Tuple<int>>(WMIMethodName.SystemPerMode).Item1; }
```

⇒ **官方与蛟龙开源项目的子命令表逐项一致**：
`2 = LongPower` · `3 = ShortPower` · `4 = CpuTempWallState`

三个值得注意的细节：
1. **功耗墙只有 Set，没有 Get** ⇒ 印证"功能号 23 只写不读"（我们现在就是这么告诉机主的）
2. **温度墙有 Get，但它读的是功能号 8（`SystemPerMode`）的 `Item1`** —— 不是功能号 23。
   ⚠️ 这看起来是官方的写法；真机诊断里功能号 8 读到的是 `0`（模式值），
   所以这个 `GetCPUTempWall` 是否真能拿到温度墙，**存疑**，需真机验证
3. **官方没有"开启"步骤** —— 它直接写 `[2,值]/[3,值]/[4,值]`，
   而蛟龙开源项目是"先写阈值、最后发 `0x0D` 启用"。
   ⇒ 两条路子在"是否需要一个显式 enable"上**不一致**，需真机确认

### 官方协议层实现（`BLD.WMIOperation.WMIMethodServices`）—— 完全印证我们的理解

```csharp
private static byte[] _MakeMethodPrams(WMIMethodType t, WMIMethodName n) {
    byte[] a = new byte[32];        // 全 0
    a[1] = (byte)t;                 // 250=Get / 251=Set
    a[3] = (byte)n;                 // 功能号
    return a;
}
private static byte[] _MakeMethodPrams(...) { ... }
public static T GetValue<T>(WMIMethodName n) { ... ExcMethod(...) ... }
public static bool SetValue(WMIMethodName n, byte[] v) { ... array[4+i] = v[i]; ... }

public static Tuple<bool, byte[]> ExcMethod(byte[] inData) {
    if (inData.Length != 32) return ...false...;
    ManagementObject mo = new ManagementObject("root\\WMI",
        "MICommonInterface.InstanceName='ACPI\\PNP0C14\\MIFS_0'", null);
    ManagementBaseObject p = mo.GetMethodParameters("MiInterface");
    p["InData"] = inData;
    byte[] outData = mo.InvokeMethod("MiInterface", p, null)["OutData"] as byte[];
    return new Tuple<bool, byte[]>(true, outData);
}
```

⇒ **`byte[32]` / `InData[1]=250/251` / `InData[3]=功能号` / 值从 `InData[4]` 起 /
类 `MICommonInterface` / 方法 `MiInterface` / `InData`→`OutData`** —— 与我们的实现**逐项一致**。

⇒ 官方**把实例名硬编码成 `ACPI\PNP0C14\MIFS_0`**，而**我们做了候选名 + 枚举兜底**
（因为机器 C 是 `MIFS_0`、机器 B 是 `MIFS`）⇒ **我们的实现比官方更稳**。

⇒ 读多值时的解析规则（可参考）：
```csharp
Tuple<int,int>    → Item1 = (Out[5]<<8) + Out[4];  Item2 = (Out[7]<<8) + Out[6]   // 小端 16 位
Tuple<int,int,int>→ Out[4], Out[5], Out[6]                                        // 各一字节
其他              → Out[4]                                                        // 单字节
失败              → -1 / -1,-1 / 255                                              // 不是静默
```

### 官方**没有**自定义档（功能号 8 值 3）

```csharp
public static void CLISetPerformaceMode(byte b) {
    switch (b) {
        case 0: SetPerformaceMode(WMISperMode.BalanceMode);     break;
```

**宝龙达的功能号 8 不支持"自定义档 = 3"**。

## 八、结论汇总

| 问题 | 结论 |
|---|---|
| 能不能从静态材料挖出厂默认阈值？ | **不能，因为它不存在** —— 阈值完全由 Host 下发，固件不预设 |
| 那基线是什么？ | **模式 0 = 不做阈值控制 = 充到 100%**，这个可以从静态材料完全确定 |
| 还需要机主先用官方控制台记基线吗？ | **不需要**（对充电阈值）。写之前确保模式 0，回滚发 `0x0F` 恢复命令即可 |
| XRAM `0x8153`/`0x8154` 可读吗？ | **可读可写**（那个项目实测回读成功 + 代码有读回校验） |
| 读它需要什么？ | **端口 I/O 能力**（`0x62/0x66`+`0x92/0x93`，或官方的 `0x2E/0x2F`），现有 H2RAM 通道到不了 |
| 地址表可信吗？ | **三重确认**：固件 `MOV DPTR` 硬编码（最强）+ 固件控制链 + 与开源项目逐项吻合 |
| 官方控制台有充电阈值吗？ | **没有**（88 类型里无 Battery/Charge；`ECRW_Tool` 只有风扇） |
| 官方有没有 EC 读写能力？ | **有**，走 `RyzenSmu.Smu` + WinRing0 + 端口 `0x2E/0x2F`，`ushort` 16 位索引可达任意 XRAM |
| 官方支持自定义档（功能号 8=3）吗？ | **不支持**（`CLISetPerformaceMode` 只映射 0/1/2）—— 第二个独立确认 |

## 1. 审计结论表（逐条：事实 / 设计规则 / 实际行为 / 风险 → 处置）

### ① MachineIdentity 缺设计里的事实
| 项 | 审计事实（修前） |
|---|---|
| 事实集 | 只有 `Board/BoardSource/BaolongdaWhitelisted/GpuGeneration/GcuServiceInstalled/Summary` |
| 设计 §1 要求 | `board`、`model`、`gen`、`gcuInstalled`、`mifsClass`、`projectId`、`wujieApu` … |
| 实际影响 | 规则只能靠板号/代际/服务存在性；无法表达「MICommonInterface 存在但没装 GCU」→ 老接口机型必然被声明成 GCU |

**处置（已修）**：`MachineIdentity` 补齐 → `Model/ModelSource`、`MifsClass/MifsClassPresent/MifsLegacyCompatible`、`ProjectId/ProjectIdSource`、`GcuVariant/GcuVariantFamily`、`WujieApu/WujieApuSource`，每项都带来源、失败退化 Unknown/空，全部只读（注册表 / WMI 类查询 / 已缓存代际）。
- `model`：复用 `BoardWhitelist` 已缓存的 `Win32_ComputerSystem.Model`（兜底 `SystemProductName`），不重复 WMI。
- `mifsClass`：只读查询 `root\WMI:MICommonInterface` 类是否存在 + 记录类 GUID 是否等于老同方 `B60BFB48-…`（`LegacyMifsWmi.TryCreate` 的硬校验值），**2 s 上限**。
- `projectId`：`HKLM\SOFTWARE\OEM\...\ItemSupport`（ItemSupport 优先、GpuConfig 兜底）的 `BIOS_PROJECT_ID` 系列别名。
- `gcuVariant`：`HKLM\SOFTWARE\L-Mechrevo\GcuVariant` 原值 + `GcuVariantFamily` 家族归一。
- `wujieApu`：型号/板号关键字（无界/WUJIE/WJXY）+ AMD CPU + 无 NVIDIA 独显；与 `WujieSmuGate` 的 `ApuOk` 同方向，但**不触发 SMU 探测**（见 §4 风险）。

### ② Router 没有 LegacyMifs 规则 / fallback 固定 Gcu
| 项 | 审计事实（修前） |
|---|---|
| 规则表 | 只有 3 条：白名单→Baolongda、GCU 服务→Gcu、`gen 30/40/50`→Gcu；兜底 Gcu |
| 设计 §1 | 规则 4 必须存在：`mifsClass && !gcuInstalled → LegacyMifs`；规则 2 应为 `gen && gcuInstalled` |
| 实际影响 | 无 GCU 的老接口机型（MICommonInterface 存在）没有规则可命中 → 落到兜底 **Gcu**（未连接）；`gen` 单独也能声明 GCU（代际≠GCU 通路存在） |

**处置（已修）**：规则表改为 4 条 + 兜底：
1. 板号白名单 → Baolongda
2. `gen ∈ {Gen30,Gen40,Gen50} && gcuInstalled` → Gcu
3. `gcuInstalled` → Gcu
4. `MICommonInterface(legacy GUID) && !gcuInstalled` → LegacyMifs
5. fallback → Gcu（未连接如实提示）
并给 LegacyMifs 增加能力声明（`RequiresFacts=["mifsClass"]`）；`DescribeDeclarations` 现在会列出三个后端。
> 行为变化只发生在「有 legacy MIFS、无 GCU」的机型：从“声明 Gcu（必然连不上）”改为声明 LegacyMifs（与实际探测一致）。其余机型后端结果不变（规则序号/说明可能变化）。

### ③ CandidatesFor 实际后端与路由声明可能不一致
| 项 | 审计事实（修前） |
|---|---|
| 候选顺序 | `CandidatesFor` 只特判 `preferred==Baolongda`；声明 `LegacyMifs` 时仍先跑 `gcuGate → baolongda → legacyMifs`（白跑两次探测） |
| 实际 vs 声明 | 探测循环直接返回实际后端，**从不记录 declared 与 actual 的差异**；`ActiveRoute` 由连接对象推导，无法回答“声明的是谁” |
| 风险 | 白名单宝龙达机型若 `MICommonInterface` 缺失，会静默退到 legacy/GCU，日志里看不出“声明被兜底换掉” |

**处置（已修）**：
- `CandidatesFor(LegacyMifs)` 新增分支：老接口第一，再按原安全顺序兜底；其它声明顺序逐位不变。
- `Probe()` 新增：`候选顺序=…`、**`declared=… · actual=… · 一致=…`** 日志；不一致走 `WriteError`（默认日志级别可见），并写明「已按实际后端运行，不静默换后端」。
- 新增 `MechrevoBackendOrder.LastActualKind`（实际探测结果，供诊断/属性对比）。
- `MechrevoHw` 新增 `DeclaredRoute` / `RouteDeclarationMatchesActual`（纯审计属性，**不参与任何硬件判断**）。
- **严格性取舍**：声明不命中时仍允许候选兜底（不破坏已知机型），只确保“差异可见”；⛔ 未改成“声明失败就整体失败”。

### ④ `[gate] 机型分类` / 诊断包是否真正共用 MachineIdentity
| 项 | 审计事实（修前） |
|---|---|
| `[gate] 机型分类` | **不存在**；只有 `[gate] 非宝龙达（backend=…）`（且只在 GCU 兜底/legacy 两条路径） |
| 诊断包 | `DiagnosticBackendRouteInfo.Build()` 自己重新 `Collect()`，且**只有声明、无实际后端/无声明对比** |
| 一致性 | 运行日志的机型事实只出现在 `[强化机型分流]` 一行（Info 级，默认级别不落盘） |

**处置（已修）**：
- 新增 `[gate] 机型分类：<机型事实> ⇒ declared=… · actual=… · 一致=…`（`MechrevoHw.ConnectAsync` 探测后一行）；事实**直接复用** `BackendRouter.LastDecision.Identity`（同一实例），不重读 WMI/注册表；不一致升级为 `WriteError`。
- `BackendRouter.LastDecision` 成为运行期唯一路由事实来源（日志/诊断/属性三方共用）。
- 诊断包新增：运行期事实 vs 诊断重采事实对比、路由重算纯函数校验、实际后端、**声明 vs 实际**、能力声明清单、规则矩阵自测。
- ⚠️ 默认日志级别为“仅错误”时，`[强化机型分流]`/`[gate]` 的 Info 行不落盘（既有分级规则，未改）；诊断包与 `LMECHREVO_LOG_LEVEL=all` 可见（§3 证据即用此方式抓取）。

### ⑤ 板号白名单 / GPU 代际 / GcuVariant 兜底判据
| 判据 | 审计事实 | 处置 |
|---|---|---|
| 板号白名单 | `BoardWhitelist.Matches`：精确 `MRID6` + `MRID6-` 连字符前缀（大小写/空白不敏感）；`MRID60`/`MRID6A` 不会被误收；读不到按“不是宝龙达” | ✅ 无漏判，未改 |
| 板号取证 | 注册表 BaseBoardProduct → WMI BaseBoard → SystemProductName/WMI Model（后两者必须含 `MRID6`） | ✅ 未改（本机取证 `GM5HG0A(reg.BaseBoardProduct)`） |
| GPU 代际 | `GpuGenerationProvider.Current()`（本机 `Gen40`，`dGPU generation resolved` 日志可查）；读不到=`Unknown` | ✅ 识别本身未改；**规则**改为“代际 + 已装 GCU”才声明 GCU |
| GCU 服务 | `MechrevoHw.IsGcuServiceInstalled`：服务注册表键（GCUBridge/GCUService）→ ItemSupport 快照兜底 | ✅ 未改 |
| GcuVariant | 注册表 `HKLM\SOFTWARE\L-Mechrevo\GcuVariant`；`40B→40` 家族归一 | ✅ 新增为机型事实（本机 `40`/`40`） |

### ⑥ 是否有可运行的机型分流自测 / 探针
| 项 | 审计事实（修前） |
|---|---|
| 自测 | 无（`GcuVariantFamily` 有自测，但机型分流没有） |
**处置（已修）**：
- `BackendRouter.RunSelfTest()`：纯函数规则矩阵（9 条规则断言 + 3 条能力声明断言 = **PASS=11**），已内嵌进诊断包。

## 4. 仍无法验证 / 风险（如实记录）

1. **宝龙达真机未实测**：`MRID6`（30 系 6800H+3070Ti）与 `MRID6-23`（40 系 7945HX+4070）不在手边。
   规则矩阵用合成事实验证；真机需在诊断包里看 `[gate] 机型分类`/`[强化机型分流]` 是否 `declared=Baolongda` 且 `actual=Baolongda`。
2. **老接口真机未实测**：本机 `mifs=absent`，无法验证 `LegacyMifs` 真实探测；规则/候选顺序已按设计写好，真机日志会给出实际结果。
3. **完整 UI 启动未做**：`tools/dev/wpf-p0/app.manifest` 是 `requireAdministrator`，普通用户启动被系统拒绝（本轮实测启动后进程立即退出、日志目录未创建）。
   遵守任务「非管理员启动」要求，**未提权启动**；证据改由非管理员探针调用**同一条只读路径**（`MachineIdentity.Collect` / `BackendRouter.DecideAndLog` / `MechrevoBackendOrder.Probe`）与**同一个日志辅助方法**（`LogMachineRouteGate`）抓取。
4. **`wujieApu` 事实是简化口径**：为避免在机型识别阶段触发 SMU/PawnIO 探测，只判“型号/板号关键字 + AMD + 无 NVIDIA 独显”，未含 family/SKU 命中与 `SmuAvailability`；与 `WujieSmuGate` 的 `ApuOk` 同方向但可能更保守。事实来源已在 Summary 里注明。
5. **`projectId` 依赖 GCU 安装器写下的注册表**：未装 GCU 的机型为空（如实 Unknown），不新造 EC 读通道。
6. **声明 Baolongda 但 `MICommonInterface` 缺失**：按设计「机型优先」仍声明 Baolongda，实际探测会兜底到 legacy/GCU，并记 `WriteError` 不一致；这是“不破坏已知机型”的取舍（未改成声明失败即整体失败）。
7. **`MachineIdentity.Collect` 成本**：新增一次 `MICommonInterface` WMI 类查询（2 s 上限），仅在「路由一次」与「诊断包」调用；启动路由在 `Task.Run` 内，不阻塞 UI。
8. **`GpuGenerationProvider.Current()` 有既有写配置副作用**（`dgpu_generation` 指纹落盘），本轮未改；严格意义上它与“纯只读事实”还有差距，属历史行为。

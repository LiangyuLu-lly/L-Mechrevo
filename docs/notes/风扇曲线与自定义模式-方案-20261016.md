# 风扇曲线与自定义模式 —— 开源实现调研与落地方案

日期：2026-10-16
状态：**仅调研与方案，未改任何代码**
起因：用户提出「蛟龙和斗战者控制台貌似都有比较完善的自定义和风扇曲线功能」

## 0. 一句话结论

**宝龙达可以做风扇曲线，而且不需要 EC 端口或内核驱动** —— 斗战者在 `MICommonInterface` 这套**同一个 WMI 接口**上，用功能号 20（手动使能）+ 21（设转速）实现了完整的手动风扇控制。这两个功能号我们**已经登记过、也已验证可读**，只是从未验证过**写**。

自定义模式同理：CPU 侧（PL1/PL2/温度墙）走功能号 23，宝龙达也有该功能号。

**但两件事必须先真机验证，否则不能开工**（详见 §6）。

## 2. 协议事实（可直接用）

### 2.1 风扇 —— 斗战者证明功能号 20 / 21 是**双参数**

```csharp
// SetFanManual: MaxFanSwitch(20), InData[4]=fanType, InData[5]=enable
input[1] = 251; input[3] = 20; input[4] = fanType; input[5] = enable ? 1 : 0;

// SetFanSpeed: MaxFanSpeed(21), InData[4]=fanType, InData[5]=RPM/100
input[1] = 251; input[3] = 21; input[4] = fanType; input[5] = speed;
```
来源：`DOUZHANZHE-Control/server/api/WmiInterface.cs:166-192`

**这对我们很重要**：我们此前把功能号 20 理解成「最大风扇开关」（单参数布尔），21 理解成「最大风扇转速」。斗战者显示它们其实是**按风扇编号寻址的双参数接口**。`fanType` 0/1 对应两个风扇。

### 2.2 风扇 —— 蛟龙的 EC 侧寄存器（备查，宝龙达大概率用不上）

```
EC_ADDR_PORT = 0x4E, EC_DATA_PORT = 0x4F
Fan1_RPM_Level = 0xC836, Fan2_RPM_Level = 0xC837   // 当前档位（读）
Fan1_RPM_SET   = 0xC83C, Fan2_RPM_SET   = 0xC83D   // 设定档位（写）
0xB20  bit1 = CPU 手动使能, bit3 = GPU 手动使能
```
访问序列（`Blding64.cs:103-152`）：`0x2E←0x11, 0x2F←高字节` → `0x2E←0x10, 0x2F←低字节` → `0x2E←0x12, 0x2F←数据`。
来源：`JiaolongControl/Server/Core/Models/SysEnums.cs:15-22`、`Drivers/Blding64.cs`

### 2.3 CPU 自定义模式 —— 功能号 23 的子命令

public enum CPUPower : byte {

用法（`CpuController.cs:43-76`）：`SetValue(功能号23, [LongPower, lp])` / `[ShortPower, sp]` / `[CpuTempWallState, tw]` / `[OpenState]` / `[CloseState]`。
来源：`JiaolongControl/Server/Core/Models/SysEnums.cs:3-10`

## 3. 可借鉴 / 不可借鉴

### 可直接借鉴（做法，非代码）

| 项 | 来源 | 理由 |
|---|---|---|
| 功能号 20/21 的双参数用法 | 斗战者 | **纯协议事实**，宝龙达同接口 |
| 功能号 23 的子命令表 | 蛟龙 | 同上，且宝龙达有该功能号 |
| 回差策略（升温即写、降温需过 3°C） | 斗战者 | 纯算法，防抖有效 |
| 交叉散热联动（共享热管 ×0.85） | 蛟龙 | 纯算法，双扇机型合理 |
| 非对称 EMA 平滑 + 升温/降温斜率限制 | 蛟龙 | 纯算法，护风扇噪音 |
| 偏离检测 + 分级恢复 | 斗战者 | 纯工程经验，很有价值 |
| 启动清理 / 退出恢复 / 睡眠恢复 | 斗战者 | 防"手动模式残留导致风扇异常" |
| Tick 防重入 | 斗战者 | 防并发写硬件 |
| 原子写配置（tmp + Move） | 斗战者 | 防配置损坏 |
| 只在值变化时写 | 蛟龙 | 减少硬件写次数 |

### 不可借鉴

| 项 | 原因 |
|---|---|
| 蛟龙的 EC 端口 I/O（`0x4E/0x4F`） | 需 `JiaoLongDriver64` 内核驱动；**宝龙达无此通道**（真机已确认打不开 `\\.\ACPIDriver`，无 `UWACPIDriver`） |

| 斗战者的 EC 物理内存读 GPU 温度（`0xFE8004E0`） | 需第三方内核驱动、窗口对不上、板号特定（已另行否决） |

| `powercfg` 输出正则解析 | 依赖系统语言与文本格式，脆；我们已有更直接的通道 |

## 4. 我们的设计方案

### 4.1 分层

```
曲线定义（数据）  →  决策器（算法）  →  下发（后端路由）  →  回读诊断
FanCurveProfile      FanCurveEngine       TrySetFanSpeedVia…    FanCurveRuntime
```

关键：**决策器与下发解耦**。曲线、插值、平滑、回差这些是纯逻辑，与后端无关；能不能下发、怎么下发，交给已有的路由层。这样将来加 ACPI/EC 后端时，决策器一行不用改。

### 4.2 数据结构

```csharp
// 曲线点：温度 → 目标转速
public readonly record struct FanCurvePoint(int TempC, int Rpm);

// 一条曲线
public sealed class FanCurveProfile {
    public string Id;                 // "cpu" / "gpu" / "large" / "small"
    public List<FanCurvePoint> Points;// 升序，2~16 点
    public int HysteresisC = 3;       // 回差
    public int IntervalMs  = 1000;    // 轮询周期
    public bool Enabled;              // 是否正在接管
}
```

**转速用 RPM 还是占空比？**
我们现有的 `BaolongdaFanCurveStore` 用的是「温度 + 占空比」，而两个开源项目**都用 RPM**。建议改为 **RPM**，理由：
1. 功能号 21 的入参就是 `RPM/100`，用 RPM 少一次换算；
2. 宝龙达**没有可靠的 max RPM**（我们此前已确认：界面百分比一直显示不出来，就是因为没有分母）；
3. 用占空比就必须有 max RPM，否则算不出 byte。

⚠️ 这会让既有 `BaolongdaFanCurveStore` 的存档格式不兼容 ⇒ 需要迁移或直接标记为未启用。

### 4.3 下发路径

```csharp
// MechrevoHw 新增意图方法（沿用本会话模板）
internal bool TrySetFanManualViaBackend(int fanIndex, bool enable, out bool confirmed);
internal bool TrySetFanSpeedViaBackend (int fanIndex, int rpm, out bool confirmed);
```
- 首行 `if (_baolongda?.Wmi == null || _disposed) return false;` ⇒ 非宝龙达原路走
- 内部走功能号 20 / 21，**写前试读、写后回读确认**（沿用既有做法）
- 转速换算 `(byte)(rpm / 100)`，夹紧到合法区间
- 日志用 `Logger.WriteError`（默认「仅错误」级别可见）

### 4.4 决策器（照搬算法，不照搬代码）

```csharp
// 每 tick：
//  1. 取温度（CPU=功能号22；GPU=现有 NVML/LHM 链）
//  2. hotspot = max(cpu, gpu)         // 斗战者做法
//  3. 查曲线（线性插值，蛟龙做法）
//  4. 回差判断（斗战者 ShouldWrite）   // 升温即写、降温需过 3°C
//  5. 平滑（非对称 EMA，蛟龙）         // 可选，先不做
//  6. 交叉散热联动（蛟龙 0.85）        // 双扇机型
//  7. 下发 + 回读
//  8. 偏离检测 → 分级恢复（斗战者）
```

**建议第一版实现的顺序**：3 → 4 → 7 → 8，先不做 5、6。理由：曲线查找 + 回差 + 下发 + 偏离检测已经能跑通且可验证；平滑与联动是体验优化，可以在第二版加。

### 4.5 生命周期（必须做，安全边界）

| 时机 | 动作 |
|---|---|
| 启动 | **先退出可能残留的手动模式**（`SetFanManual(0/1, false)`）—— 斗战者的做法，防上次被强杀 |
| 启用曲线 | 每 tick 持续声明手动使能（斗战者注释：防 EC 固件定时器退回自动） |
| 禁用曲线 | 退出手动 + 恢复原模式 |
| **进程退出** | **必须**恢复固件控制（`Dispose` + `AppDomain.ProcessExit` 双保险） |
| 睡眠恢复 | 重置内部状态，强制重发一次 |
| 温度无效 | 跳过本 tick，不写硬件（斗战者做法） |

⚠️ **「进程退出恢复」是这类功能的头号风险**。如果程序被强杀而手动模式没退出，用户会面对一个"风扇按旧曲线狂转、且控制台认为没在控制"的状态。斗战者专门在构造时做**启动清理**，我们必须同样做，而且**退出恢复要放在最不可失败的位置**。

### 4.6 与现有代码的衔接

- **`BaolongdaFanCurveStore.cs`**：它的注释写着 `mode.Route != PerfModeRoute.FirmwareSlot` 时**直接跳过不落盘** ⇒ 这个假设是错的（见 §5）。改为**独立于档位路由**：曲线是独立功能，不挂在 `FirmwareSlot` 上。
- **`FanWatchRunner.cs`**（我们的 `--fan-watch`）：已经有了读双通道转速与温度的能力 ⇒ 正好用来**验证曲线是否生效**，可扩展成"曲线调试视图"。
- **`TrySetFanManualViaBackend` / `TryReadFanSpeeds` / `PrepareFanManualControl()`**：已有手工风扇控制的雏形，应当在它上面演进，而不是另起一套。
- **`PerfMode*` 与风扇曲线解耦**：见 §5。

## 5. 一个必须纠正的既有假设

我们此前把「自定义档」映射成 `PerfModeRoute.FirmwareSlot`，并让风扇曲线依赖它。参考实现显示**这个模型是错的**：

- 蛟龙：`CpuFanCurve` / `GpuFanCurve` 存在**应用自己的配置**里，由 `AutoFanControl` 轮询温度写转速 ⇒ **风扇曲线是软件功能，与固件槽无关**
- 斗战者：`fan-curve.json` 同样是应用自己的配置，走 `FanCurveService` 定时器 ⇒ **同上**

**正确的关系**：
```
「档位」（静音/平衡/狂暴/自定义）  → 后端模式切换（功能号 8 / 23）
「风扇曲线」                        → 独立软件引擎（功能号 20/21）
两者正交：切档不换曲线，曲线不随档位存
```

**修正方向**：把档位与风扇曲线**解耦**。档位负责模式切换，曲线负责风扇。`BaolongdaFanCurveStore` 去掉对 `FirmwareSlot` 的依赖。

⚠️ 这条与路由抽象（`docs/notes/后端路由抽象-设计-20261016.md`）**正交**，建议独立排期，别混在一个改动里。

## 6. 宝龙达可行性 —— 以及必须先验的两件事

### 6.1 结论

| 能力 | 宝龙达可行性 | 依据 |
|---|---|---|
| 风扇曲线（软件引擎） | **可行**（待验证写入） | 功能号 20/21 同接口；斗战者已证双参数用法 |
| 手动风扇使能 | **可行**（待验证写入） | 功能号 20 |
| 手动转速下发 | **可行**（待验证写入） | 功能号 21，单位 RPM/100 |
| CPU 功耗墙 / 温度墙 | **可行**（待验证写入） | 功能号 23 子命令；诊断包显示该功能号可读 |
| 自定义档切换 | **可行** | 功能号 8（已验证可读，写入待验） |
| GPU 频率/功耗 | **不可行**（厂商侧无接口） | 三项目全走 NVAPI/nvidia-smi；我们只能用 NVML |
| ITSM 模式路由（斗战者的 `0xE4`） | **用不上** | 需 EC 通道，宝龙达没有 |

### 6.2 ⚠️ 必须先真机验证的两件事

**这两条不验证，后面全白做。**

**① 功能号 20 / 21 的写入是否被固件接受**

我们目前只验证过**读**（诊断包：功能号 20、21 均可读）。写从未试过。验证方法要**保守**：
- 先只做**读 + 一次极小写入试验**（例如设一个安全的中间档，观察风扇是否响应、随后立即退出）
- 观察点：功能号 13 的转速读数是否跟随变化；功能号 20/21 读回值是否反映写入
- ⚠️ 若写入被拒或风扇行为异常 ⇒ **立即退出手动模式**，并放弃这条路
- ⚠️ 这一步**有硬件影响**（风扇转速），必须用户在场、且先写清回滚办法

**② 宝龙达是否有"模式区间限制"**

斗战者的 ITSM 路由表显示：不同模式（silent/office/beast/gaming）下，EC **只接受特定区间的转速**，超出会被拒绝。宝龙达没有 EC 通道，但**可能有类似的区间限制存在于固件里**。
- 如果**有** ⇒ 需要类似的路由 + 钳位，且得摸清区间表
- 如果**没有** ⇒ 直接写 0~68（6800 RPM）即可，实现简单很多
- 验证方法：在手动模式下试几个档位，看哪些被接受、哪些被拒

### 6.3 单点风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **退出未恢复** | 最严重：程序被杀后风扇失控 | 启动清理 + 退出恢复双保险 + 看门狗 |
| 温度读不到 | 曲线失效 | 跳过本 tick 不写硬件（斗战者做法） |
| 转速区间被拒 | 曲线部分档位无效 | 钳位 + 日志如实报告"该档被拒" |
| 与厂商控制台竞争 | 双方都写同一寄存器 | 斗战者 `SetFanSpeed` 前先关 `MaxFanSpeedSwitch`，值得借鉴 |
| GPU 温度来源弱 | 我们靠 NVML，有 31 秒启动空窗 | 先修那条（已另派），曲线本身不依赖它（可用 CPU 温度兜底，蛟龙就这么做） |

---

## 7. 分步计划

| 步 | 内容 | 工作量 | 可验证性 | 风险 |
|---|---|---|---|---|
| **0** | **真机验证 §6.2 的两件事** | 小（需机主配合） | 高 | **有硬件影响**，需用户在场 |
| **1** | 数据模型改造：曲线改用 RPM；`BaolongdaFanCurveStore` 去掉 `FirmwareSlot` 依赖 | 中 | 高（纯数据，本机可验） | 低 |
| **2** | 决策器：曲线插值 + 回差判断（纯逻辑，可单测） | 中 | **很高**（不碰硬件，可写测试） | 低 |
| **3** | 下发路径：`TrySetFanManualViaBackend` / `TrySetFanSpeedViaBackend` + 回读确认 | 中 | 中（本机是 GCU 机型，宝龙达分支走不到 ⇒ 需真机验） | 中 |
| **4** | 生命周期：启动清理 + 退出恢复 + 睡眠恢复 + Tick 防重入 | 中 | 中 | **高**（做错会导致风扇失控） |
| **5** | 偏离检测 + 分级恢复 | 小 | 中 | 低 |
| **6** | 界面：曲线编辑器（我们已有曲线图控件）+ 运行状态显示 | 中 | 高（本机可看） | 低 |
| **7**（可选） | 平滑（EMA）+ 交叉散热联动 | 小 | 中 | 低 |
| **8**（独立） | 自定义模式：功能号 23 的 PL1/PL2/温度墙接入 | 中 | 中 | 中（同样是硬件写入） |

**建议顺序**：0 → 1 → 2 →（3+4 一起，因为生命周期与下发不能分）→ 5 → 6 → 7。第 8 步独立排期。

**第 2 步特别值得先做**：决策器是纯逻辑，可以写单元测试，不碰硬件、不受"本机是 GCU 机型"限制。这是整个功能里唯一能高置信度验证的部分，应该把它做扎实。

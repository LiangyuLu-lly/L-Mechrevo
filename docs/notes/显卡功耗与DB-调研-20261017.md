# 显卡功耗调节 & Dynamic Boost（DB）调研（2026-10-17）

> 起因：机主问「宝龙达原版或开源项目有没有显卡功耗调节」→「蛟龙开源项目有吗」→「NVAPI 能不能读到 DB」。
> 本文只记**事实与结论**，供后续做「自定义档 → 显卡功耗上限」时直接查。

---

## 一、三份材料有没有「显卡功耗调节」

| 来源 | 有 TGP / 显卡功耗？ | 有 DB（动态加速）？ | 实现 |
|---|---|---|---|
| **原厂 40 系控制台**（v0.3.15） | ❌ 零命中（`Tgp`/`DynamicBoost`/`GpuPower`） | ❌ | 只有 GPU 温度/频率/显存/占用**显示** |
| **7.3 第三方** | ❌ | ❌ | 只有 `SetGPUClockLock`（锁频）、`SetGpuMode`（独显直连） |
| **`JiaolongControl`**（MIT） | ✅ **有** | ❌ | **NVML**：`GetPowerManagementLimitConstraints` → 钳制 → `SetPowerManagementLimit` |
| **`DOUZHANZHE-Control`**（GPL-3.0 · 只取事实） | ✅ 有 | ❌ | **NVAPI** `SetPowerLimit`（W→mW），并按模式保存/恢复 |

### 蛟龙开源（`JiaolongControl`）的具体写法（事实）

```
JiaoLongControl\Server\Core\Controllers\NvidiaGpuController.cs
  GetGpuPowerLimitRange()  → NvAPIWrapper: gpu.PerformanceControl.PowerLimitInformation
                             info.MinimumPowerInPCM / MaximumPowerInPCM
  SetPowerLimit(watts)     → NvmlInterop.GetPowerManagementLimitConstraints → 钳制 → SetPowerManagementLimit(mW)
                             （注释明确：NVML 单位是毫瓦，nvidia-smi -pl 是瓦）
  LockGpuClock / ResetGpuClock → NvmlInterop.SetGpuLockedClocks / SetGpuLockedClockFloor / ResetGpuLockedClocks
```

底层就是 NVML 两条官方导出：

```
nvmlDeviceGetPowerManagementLimitConstraints(device, out min, out max)
nvmlDeviceSetPowerManagementLimit(device, milliwatts)
```

⇒ **不依赖 GCU、不依赖厂商 WMI**，我们现有 `NvmlHelper` 同源，加两条导出即可。

## 二、DB（Dynamic Boost / PPAB）到底能不能读

**不能（没有公开接口）。**

| 通道 | 能读 DB？ | 说明 |
|---|---|---|
| NVAPI（NvAPIWrapper） | ❌ | `PowerLimitInformation` 只有 `MinimumPowerInPCM` / `MaximumPowerInPCM`，**没有 DB 字段** |
| NVML | ❌ | 只有 `PowerManagementLimitConstraints` / `DefaultLimit` / `GetPowerUsage`，没有 DB |
| NVIDIA 控制面板 / `nvidia-smi` | ❌ | 都不显示 DB 档位 |
| **厂商固件字段** | ✅ | 我们 GCU 路径里就有：`GpuDynamicBoostSwitch` / `GpuDynamicBoost`（`CustomModeForm` 的「GPU 动态加速」行） |
| **宝龙达 WMI** | ❌ | 功能号表 8~23 里**没有** TGP/DB |

- DB = **PPAB（Power Policy Adjustment Budget）**，由 **NVIDIA 驱动 + OEM EC/ACPI** 协同 ⇒ 厂商才能给"档位"语义；
- 能**间接推断**：`nvmlDeviceGetPowerManagementDefaultLimit`（≈基础 TGP）与 `...LimitConstraints` 的 `max` 之差 ≈ DB 最大余量 —— ⚠️ 但不少机型 `max` 就等于基础 TGP，**靠差值判断不可靠**；
- 想在宝龙达上读真实 DB 档位 ⇒ 只能走 **EC（PawnIO `0x62`/`0x66` XRAM）只读探测**，而**地址未知、无任何参考实现指认** ⇒ 不建议为"显示一个数字"开这个口子。

## 三、结论与决策（待办）

1. ✅ **做「显卡功耗上限」**：NVML `min~max` → 钳制 → 写 → **回读确认**；失败/不支持 ⇒ **不显示滑块**（宁可不显示，不显示错的）。
   - 文案建议「显卡功耗上限」（它天然覆盖 DB 余量区间，不承诺"这是 DB 值"）；
   - 仅宝龙达启用；GCU 机型仍走厂商 `GpuConfigurableTGPTarget`（逐位不变）。
2. ⛔ **不做「DB 数值显示」**：NVAPI/NVML 都没有；EC 侧无依据。
3. ⏳ 将来若要支持 DB 档位（5/10/15W 之类）：必须先有宝龙达 EC 文档，或用只读抓包确认官方控制台是否真的写过这类命令 —— 且官方 40 系控制台**没有** DB 入口，**大概率不存在**。

## 五、补充：G-Helper 的 DB 做法（2026-10-17 追加）

素材：`https://github.com/seerge/g-helper`（MIT）—— 本地 `git clone` 到 `%TEMP%\_ghelper` 做静态查证（只取事实）。

### 事实

```csharp
// AsusACPI.cs
public const int PPT_GPUCPU9C = 0x0012009C;  // GPU to CPU Dynamic Boost, 5W steps
public const int PPT_GPUC0    = 0x001200C0;  // NVIDIA GPU Boost
public static int MaxGPUBoost = 25;
```

- **写**：`ModeControl.DeviceSet(AsusACPI.PPT_GPUCPU9C, gpucpu, ...)`（GPU→CPU 预算，5 W 步进）、
  `Fans` 里的 GPU boost 滑块写 `PPT_GPUC0` —— 全是 **ASUS 自己的 ACPI/WMI 方法**；
- **最大值不是读出来的**：`AppConfig.DynamicBoost5/15/20()` 按**机型表**决定 `MaxGPUBoost`
  （`GZ301ZE`=5W、`FX507ZC4/GA403UM/GU605CP/…`=15W、`GU605/GA605/GU405`=20W，默认 25W）；
- **当前值**：`AppConfig.GetMode("gpu_boost")` —— G-Helper **自己存的值**，只用于 UI 回显；
- 支持性判据：`Program.acpi.IsSupported(PPT_GPUC0)`（厂商 ACPI 方法存在与否）。

### 结论

⭐ **G-Helper 也不"读"DB** —— 它的做法是「**按机型表给上限 + 写厂商 ACPI + 自己记住值**」。

⇒ 三个厂商三条完全不同的通道，**不存在跨厂商的 DB 读接口**：

| 厂商/平台 | DB 通道 | 类型 |
|---|---|---|
| **ASUS**（G-Helper） | ACPI/WMI 方法 `0x0012009C` / `0x001200C0` | 写 + 机型表 |
| **同方（GCU）** | EC RAM `0x743` 控制字节 / `0x745` 目标 / `0x746` 最大 TGP | 读 + 写 |
| **宝龙达** | ❌ 无（WMI 功能号表没有，EC 未探测） | — |

⭐ **可借鉴的工程做法**（与我们的 P1/P2 一致）：机型表给范围 + LM 自存当前值 + 写后回读；
⛔ 但 **ASUS 的 ACPI 方法在宝龙达上不存在**，不能照搬。

## 六、本机实测（开发机 · 知识储备，2026-10-17）

```powershell
nvidia-smi --query-gpu=name,power.default_limit,power.min_limit,power.max_limit,enforced.power.limit --format=csv
```

本机（同方 `GM5HG0A` · **RTX 4060 Laptop GPU**）实测：

| 字段 | 值 | 含义 |
|---|---|---|
| `power.default_limit` | **115 W** | 基础 TGP |
| `power.min_limit` | **5 W** | 驱动允许下限（`nvidia-smi -pl` 的可用下界） |
| `power.max_limit` | **140 W** | **含 DB 的上限** |
| `enforced.power.limit` | **115 W** | 当前生效值（此刻未吃到 DB） |
| `power.limit` | `N/A` | ⚠️ 该驱动/机型这一栏就是 N/A，别当读失败；看 `enforced.power.limit` |

⇒ ⭐ **DB 最大余量 ≈ `max_limit − default_limit` = 140 − 115 = 25 W**
（与 4060 笔记本常见"115W 基础 + 25W DB = 140W"完全吻合）。

### 三条纪律（写进知识储备）

1. **DB 不是独立读数**：上式的 25W 是"最多能加多少"，不是"此刻 DB 给了多少"；
2. `power.limit` 可能为 `N/A`（本机就是）⇒ 用 `enforced.power.limit` 或 NVML `nvmlDeviceGetPowerManagementLimit`；
3. 不同机型 `max_limit` 可能**不含** DB（有的 vBIOS 就把 DB 藏在别处）⇒ 该差值只能当**参考**，不能当"DB 规格"对外承诺。

### 待办（未做）

- [ ] 把 `default_limit / min_limit / max_limit / enforced` 四项加进**诊断包**的 GPU 小节
      （只读，一次 `nvidia-smi --query-gpu` 调用）⇒ 以后每份诊断包自带本机 GPU 功率档位，不必再单独问机主。
- [ ] 40 系蛟龙（4070）的那台还没测：需在那台机器上跑同一条命令（只读），把结果补进本节。

### 40 系蛟龙的参考口径（⚠️ 未实测，别当结论）

4070 笔记本常见是 **115W 或 100W 基础（+25W DB）**，但**必须**以那台机器上的
`default_limit / max_limit` 为准 —— 不同 OEM/不同 vBIOS 差异很大。

### 2026-10-17 追加实测：切到「狂暴」模式后

同一条命令、同一台机器（4060），切换性能模式后再读：

| 字段 | 平衡/其它模式 | **狂暴模式** | 说明 |
|---|---|---|---|
| `power.default_limit` | 115 W | **115 W** | BIOS/驱动静态上限，**不随模式变** |
| `power.max_limit` | 140 W | **140 W** | 同上，静态 |
| `enforced.power.limit` | **115 W** | ⭐ **140 W** | ⭐ **随性能模式变化** —— 这就是"本档实际给的 GPU 预算（含 DB）" |
| `power.draw` | 5.57 W | 5.5 W | 空载 |
| `temperature.gpu` | 39 ℃ | 39 ℃ | 空载 |
| `clocks.current.graphics` | — | 210 MHz | 空载 |

⭐⭐ **结论（对 LM 有用）**：

1. `default_limit` / `max_limit` 是**静态**的（BIOS/驱动），**不能**用来判断"当前档给了多少"；
2. ⭐ **`enforced.power.limit` 才是"本档生效的 GPU 预算"**，会随性能模式切换（115 → 140）；
3. ⇒ 这给了我们一个**可回读的验证点**：
   - 切档后读 `enforced.power.limit`，能**确认切档是否真的生效**（不是只看 UI）；
   - 自定义档写 GPU 功耗上限后，也能用它做**写后回读**；
4. ⚠️ 115→140 的 +25W 正是 DB 余量 ⇒ **狂暴模式 = 吃到完整 DB**；其它模式只给基础 TGP。
   （⚠️ 但这只证明"本机模式与预算联动"，不代表所有机型都这样。）

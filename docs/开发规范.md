# L-Mechrevo（LM）开发规范

> 本文件记录机主明确要求、必须长期遵守的开发约定。
> 位置：`docs/开发规范.md`。新增约定请直接补到对应小节，不要只写在会话里。

---

## 1. 注释规范（机主 2026-10-19 定稿，最高优先级）

### 1.1 不写来路
- **除开源项目外**，凡是由反编译、逆向、对照官方组件行为得到的知识：
  - ⛔ 代码注释里**一律不写来路**；
  - ⛔ 不出现「反编译 / 逆向 / 官方组件 / 作者版本 / 参考材料 / 内部路径 / 出处 / 依据源文件」等字样；
  - ✅ 只记录**功能本身**（这段代码做什么、为什么这样写对使用者有意义）；
  - ✅ **不确定就不写注释**。

### 1.2 只注释功能、保持简短
- 每个注释块 **≤1 行**，只描述行为；
- 删除：日期标签、⭐/✅/⛔ 装饰堆、历史演变、机主原话摘录、重复解释、参考路径；
- 明显自解释的代码，不写注释；
- 只有「非显然时序 / 安全红线 / 易踩坑点」才允许补一句说明。

### 1.3 反例 → 正例
```csharp
// ❌ 反例（写了来路）
// 依据反编译 7.3 的做法：16=2 后每 50ms 写 17
// 按作者 0.290.6 对齐：铰链效果 5 项
// 官方 GCU 组件里 RGBKB_Effect.Rainbow = 5

// ✅ 正例（只写功能）
// 先写 16=2（固定色），再每 50ms 写 17 刷色相
// 铰链灯效果：Single / Breathing / Wave / Impact / Raindrop
// 彩虹是固件原生效果，不写颜色
```

## 2. 改动范围纪律（机主 2026-10-19 强调）

- **只修已确认有问题的点**；
- ⛔ 禁止顺手改动其它通道、功能、效果表（「不要乱改导致问题扩大」）；
- 一次提交只做一件事；需要连带改动时必须先说明理由；
- 未确认的现象，先加只读日志取证，不猜着改。

---

## 3. 版本号与打包

- 打包时**数字版本号与 beta 后缀同步递增**（例：beta23.2 ⇒ `0.292.2 beta23.2`）；
- 同步位置：`source/Properties/AssemblyInfo.cs`、`installer-src/install_script.iss`（AppVerName/AppVersion/OutputBaseFilename/VersionInfoVersion/UninstallDisplayName）、两份日志标题、包名；
- **未经机主明确说「打包」，不要打包**；
- 打包流程：`dotnet build` → `dotnet publish … -o rebuild\lm_fix_build` → `py -3 tools\merge_and_clean.py --apply` → `ISCC.exe installer-src\install_script.iss`（不加 `/DNOGCU`）。

---

## 4. 交付产物规则

- 交付 DLL 时：**若本次没有中文资源（resx/Strings）改动，只给主 `L-Mechrevo.dll`**；有资源改动才连同 `zh-CN\L-Mechrevo.resources.dll` 一起给；
- 代码行尾：改文件前确认原文件是 LF 还是 CRLF，按原样写回（python 文本模式替换会整文件改行尾，踩过坑）；
- 新增/修改资源键时同步 `Strings.cs` 与中/英 resx。

---

## 5. 验证要求

- 编译必须 **0 错误、警告数不增加**（当前基线 1461）；
- 涉及硬件的改动，必须给出**日志证据**（`[light-boot]`、`[ui-build]`、`[perfmode]` 等）或真机诊断包，不写「应该没问题」；
- 本机（同方 GM5HG0A）不能验证宝龙达链路时，只做编译 + 代码走查，并注明「真机待验」；
- 诊断包归档到 `docs/diag-packs/`，文件名保留版本+时间+机型。

---

## 6. 文档与日志

- 用户可见变更写 `更新日志.txt`；技术细节/回归记录写 `修改日志.txt`（回归问题**只写修改日志，不写更新日志**）；
- 两份日志同步到 `installer-src\files\`；
- 研究结论、协议探索、脚本交接写 `docs/notes/`，并在交接文档里给出可复制路径。
